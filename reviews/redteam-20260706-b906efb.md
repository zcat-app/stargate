### Major

#### B1. Leak scan misses realistic logger encodings — no-log contract under-pinned
- **Worklist file**: `redteam/findings/open/20260706-001-leakscan-encoding-gaps.md`
- **Where**: `tests/contract/control-grpc/dpharness_test.go:378-397` (`assertNoSecretLeak`)
- **What**: The scan checks four encodings of each secret: lowercase hex, uppercase hex, base64 StdEncoding, base64 RawStdEncoding. It omits (a) base64 URL/RawURL encoding and (b) the decimal-slice rendering `[12 34 56 …]` that Go's `slog` TextHandler and any `fmt.Printf("%v"/"%+v", b)` produce for a `[]byte`. A T045/T050 implementation that logged a `TokenHash.Hash` via `slog.Info("reload", "hash", h)` (text handler) or `log.Printf("%v", hash)` would emit the hash bytes to the captured journal in decimal-slice form, and this contract test — the sole regression line for the contract's final no-log bullet (`control-grpc.md` §"ReloadTokens · Contract") — would still pass green.
- **Implicates**: Constitution Principle III "Privacy-Preserving by Construction" (logs contain no per-request/secret bytes) and Principle VII (the test is the executable guarantee). Contract `control-grpc.md` §"ReloadTokens · Contract" final bullet; `data-model.md` §1.6 "token format violations never log the offending bytes".
- **Remediation**: Extend the `encodings` map in `assertNoSecretLeak` with `base64.URLEncoding`, `base64.RawURLEncoding`, and a decimal-slice form (`fmt.Sprintf("%v", secret)` / `strings.Trim(fmt.Sprint(secret), "[]")`). Optionally also a space-separated `%d` run. Keep the current four.

### Minor

#### M1. Happy-path snapshot content never matched against sent bytes
- **Where**: `tests/contract/control-grpc/reload_tokens_test.go:43-52` and `:66-68`
- **What**: `HappyPathAppliesNewGeneration` reads the snapshot and asserts `schemaVersion`, `generation`, and `len(snap.Hashes)==1`, but never asserts that `snap.Hashes[0].Hash`/`.Salt` equal `base64(tokA.Hash)`/`base64(tokA.Salt)`. Acceptance criterion #1 explicitly requires "base64 hash/salt matching what was sent (data-model.md §1.4 shape)". A DP that persisted an empty or wrong hash/salt string (while keeping the correct value in memory for auth) would pass this test; cold-start restore (T020a) would then silently break. T020a pre-populates its own snapshot, so the persist-content correctness of a *live* `ReloadTokens` write is unverified by any case in this run.
- **Implicates**: ticket §Acceptance #1; `data-model.md` §1.4. Not a privacy leak — a contract-fidelity gap.
- **Remediation**: After `readSnapshot`, assert `snap.Hashes[0].Hash == base64.StdEncoding.EncodeToString(tokA.GetHash())` and the same for salt (encoding per §1.4). The snapshot legitimately contains these, so this adds no leak surface; `assertNoSecretLeak` scans the journal only.

#### M2. Plaintext-token leak scan is inconsistent across sub-tests
- **Where**: `reload_tokens_test.go:70-71` (happy path includes `[]byte("t020-plain-alpha"/"…bravo")`) vs `:108-109`, `:157`, `:199`, `:242` (stale/invalid/persist-failure/concurrency pass only hash+salt bytes to `assertNoSecretLeak`).
- **What**: Every sub-test drives `requireAuth`, which sends the token plaintext over the SOCKS5 auth path, so the DP sees the plaintext in all five cases. Only the happy path scans the journal for the plaintext. A DP that logged the offered SOCKS5 password on the stale/invalid/persist-failure/concurrency paths would be caught only by the happy path — coverage the harness comment claims is "belt-and-braces" but which is actually load-bearing for `socks5-auth.md` §"Auth failure does not leak token bytes". (That full surface is T025's scope, but the inconsistency here is worth closing cheaply.)
- **Remediation**: Include the case's plaintext byte slices in the `assertNoSecretLeak` call of every sub-test, matching the happy path.

#### M3. `readSnapshot` failure path prints full snapshot bytes to test output
- **Where**: `dpharness_test.go:366-368` (`t.Fatalf(... "\n%s", ..., raw)`)
- **What**: On a snapshot JSON-unmarshal failure the whole `dp-snapshot.json` is printed to test output / CI logs. That content is base64(hash)+base64(salt) of the minted tokens. These are ephemeral, test-generated tokens over known plaintexts with random salts — not user secrets — so this is not a real privacy leak, but it is a pattern that would leak real material if this harness were ever reused with production token bytes. Note `assertNoSecretLeak`'s own failure messages correctly print only the secret *index*, not the bytes — good hygiene that this one site breaks.
- **Remediation**: On unmarshal failure print `len(raw)` and the JSON error only, not `raw`; or redact to a byte count. Keep consistency with the index-only style already used in `assertNoSecretLeak`.

### Info

#### I1. `go build` in `startDP` may reach the network on a cold module cache
- **Where**: `dpharness_test.go:125-137`
- **What**: `go build ./cmd/stargate-proxy` runs in module mode; on a cold cache the Go toolchain can fetch from `proxy.golang.org`. This is Go build infrastructure, not a Stargate-product outbound call, and the acceptance container is the pinned `golang:1.26.3` image, so it is not a Principle III violation. Flagged only so a future reviewer does not mistake toolchain traffic for a Stargate outbound; consider `-mod=readonly`/`GOFLAGS=-mod=mod` with a warmed cache in CI (T076).
