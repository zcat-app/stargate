## Summary

T100 adds `BEFORE UPDATE`/`BEFORE DELETE` → `RAISE(ABORT)` triggers on `audit_log`
and hardens `configured_tokens.label` to `TEXT NOT NULL PRIMARY KEY`. The NOT NULL
hardening is correct (closes SQLite's TEXT-PK-allows-NULL quirk; compatible with
§1.1 non-empty labels). The triggers correctly block plain `UPDATE`, plain `DELETE`,
and `ON CONFLICT(id) DO UPDATE`.

**One Major finding (M1)** — `INSERT OR REPLACE` bypassed the append-only
mechanism under the default `recursive_triggers=OFF` (REPLACE's internal delete of
a conflicting PK row does not fire `BEFORE DELETE`). Verified empirically; no v1
code path used it, but the "by mechanism" claim was false for an idiomatic upsert.
**RESOLVED in-ticket** by a third trigger (`audit_log_no_replace`, BEFORE INSERT
with an EXISTS guard) that closes the overwrite at INSERT time, connection-config-
independent, plus a regression test run under the production default. Closed at
`redteam/findings/closed/20260715-001-insert-or-replace-bypasses-audit-log-append-only.md`.

## Verified absent (with evidence)

- **Per-request residues (Principle III)**: schema has no host/URL/IP/token columns;
  `aggregate_counters` hour-bucketed; `audit_log.ts` = admin-action time. Tests use
  synthetic fixed timestamps + device labels only.
- **Token-secret leak in tests**: only `new byte[32]` zero placeholders; no pepper,
  no real verifier bytes.
- **Surgical scope**: NOT NULL compatible with §1.1; triggers don't fire on Flyway
  (`flyway_schema_history` only); no new persistence surface.
- **DDL/admin bypasses (DROP TRIGGER, writable_schema)**: present and verified, but
  these are the documented THREAT-MODEL §8.3 residue. T100 does not worsen them.
  `ATTACH DATABASE` is not a bypass for the canonical table.
- **Future-migration trigger drop**: covered by `AuditLogAppendOnlyTest#appendOnlyTriggersAreInstalled`.
