## Blocking deployment decision

### B1 — The wildcard exception bypasses the constitutional bind invariant

Locations: `data-plane/internal/bind/check.go:91`,
`data-plane/cmd/stargate-proxy/main.go:96`,
`compose/docker-compose.local.yml:87`.

Compose enables `STARGATE_IN_CONTAINER=1` and a wildcard listener. The boolean
is the entire exception: it proves neither a container boundary nor a tunnel.
The unchanged constitution's Deployment Model explicitly forbids non-loopback
binding without the corresponding tunnel. FR-010's T125 amendment does not
supersede that prohibition.

Root built and ran the actual proxy natively with disposable state and pepper:

```text
native host, IN_CONTAINER=0: wildcard refused; exit=1
native host, IN_CONTAINER=1: wildcard listener opened without a container/tunnel;
                           SOCKS5 auth negotiation=05 02
```

Falsification checked the strict `Check` path, actual startup wiring, and
whether the exception verifies its premise. None prevents the demonstrated
startup. This is not a claim that an unauthenticated remote user can set the
process environment; it is a failure of the promised startup safety mechanism.

**T134** owns an evidence-led topology investigation before implementation.
It must preserve the constitution, compare alternatives, and demonstrate
loopback ingress plus actual DP egress containment. Do not merely revert the
wildcard line: that revives the original Docker publication failure.

### M1 — No-masquerade does not establish the asserted egress boundary

Locations: `compose/docker-compose.local.yml:290`,
`tests/contract/compose/network_hardening_test.go:437`,
`THREAT-MODEL.md:252` and §5.8.

The DP has a non-internal network whose explicit control disables source NAT.
The test treats failure to obtain a TCP response from `1.1.1.1:80` as evidence
of no egress. It neither observes packet emission nor covers DNS/UDP or
host/gateway/LAN paths. The threat model acknowledges DNS forwarding through
this attachment while other paragraphs still promise an all-internal topology.

Docker documents masquerading and packet filtering as distinct mechanisms;
disabling translation alone does not establish packet denial.
[Docker bridge options](https://docs.docker.com/engine/network/drivers/bridge/),
[Docker firewall behavior](https://docs.docker.com/engine/network/firewall-iptables/).

**Evidence limit:** root's single synthetic UDP probe observed a packet on the
isolated Docker bridge, but not on a physical host interface in eight seconds.
This is **not** proof of public-internet UDP exfiltration on this host. The
finding is an unsupported general isolation claim, the documented DNS
exception, and a non-discriminating test. T134 must replace assumptions about
upstream packet loss with a demonstrated enforcement boundary and positive
capture controls.

## Reproduced implementation defects

### M2 — TLS resumption bypasses a replaced CP public-key pin

Locations: `data-plane/internal/controlclient/tls.go:205–206,222–225`;
production server construction in `controlclient/server.go`.

The DP uses only `VerifyPeerCertificate` and leaves session tickets enabled.
Resumption skips that callback. An already authenticated peer with session
material and UDS access can reconnect after the operator replaces `cp.pub`.
The resumed transport retains the old authenticated identity; normal versioned
Control RPCs remain reachable over that transport.

Independent real-UDS probe using production TLS constructors:

```text
round 0: accepted; DidResume=false
replace cp.pub with an independently generated key
round 1: accepted; DidResume=true
```

This defeats wire-auth §3.1's every-handshake pin reread and §6.2's key-rotation
response without peer restart. It is a new connection, not an old connection
left open. The probe exchanged application data; it did not perform a malicious
ReloadTokens RPC. **T135** must reject the old resumed peer and accept the new
peer; use a verification callback that covers resumption or disable tickets.

### M3 — Distinct first parties receive identical Tor isolation usernames

Locations: `extension/lib/firstparty.js:109`,
`extension/background/router.js:95`.

The last-two-label approximation returns `co.uk` for both `alice.co.uk` and
`bob.co.uk`, and `github.io` for both `alice.github.io` and `bob.github.io`.
The same device password completes identical SOCKS credentials. Actual router
VM probes returned SOCKS descriptors with these collisions and `proxyDNS:true`.

The attempted falsifier was the onion-only routing restriction. It applies
to the requested destination, not its governing document: clearnet documents
can initiate onion subrequests. Constitution III/FR-002 separation is therefore
not established. No real-browser/live-circuit outcome was measured.
**T136** must derive non-colliding first-party identities and test the complete
router path, using public/private suffix cases and same-target requests.

### M4 — ReloadTokens' deadline ages before the first RPC

Locations: `control-plane/api/src/main/java/io/quarkus/stargate/control/grpc/ReloadTokensClient.java:60,115`,
`control-plane/runtime/src/main/java/app/zcat/stargate/runtime/StargateControlPlane.java:176`,
`control-plane/runtime/src/main/java/app/zcat/stargate/runtime/GrpcReloadChannel.java:50`.

The retained stub receives an absolute ten-second deadline at construction.
Token loading/persistence consumes that window, and subsequent attempts reuse
the expired deadline. The compiled production-client probe showed:

```text
initial deadline remaining sec=9
before first reload expired=true
first reload=DEADLINE_EXCEEDED
```

Local grpc-java bytecode independently confirms immediate `Deadline.after`
construction. Slow CP startup can consequently miss a revocation push and leave
the old DP generation active until a later successful synchronization. The
probe proves aging; it did not reproduce a real SQLite delay or live revocation.
**T137** must give each RPC attempt its own deadline and test an aged client
against a reachable authenticated peer. Broader restart re-push remains T132.

## Implementation decision after this audit

1. Keep the constitution and existing accepted-decision history unchanged.
2. Investigate T134's topology alternatives and T138's observation boundary
   before building further on T125/T094a. Candidate directions include
   host-loopback ingress with Unix transport into an isolated DP, or host
   loopback with separately enforced process egress restrictions. Both require
   prototypes; host networking or a shared Tor namespace alone is not a fix.
3. Restore verification trust (T139), then fix independently bounded TLS,
   browser isolation and deadline defects (T135–T137), each tests-first with
   codereview and independent redteam through the canonical driver.
4. Use the new focused tickets for remaining audit findings and source conflicts.
   Existing T123/T124/T132 retain their scopes; do not hide new fixes in them.
5. Resume the original feature queue only when the foundation's blocking
   findings have been resolved through reviewed remediation or a deliberate
   maintainer decision. Final T078/T079 and external v1.0.0 review remain due.

This report records a failed foundation checkpoint, not a reason to weaken its
acceptance criteria. No blanket rewrite or blanket re-review of every historical
commit is recommended.
