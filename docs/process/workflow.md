# Stargate ticket-driven workflow

This is the **universal workflow specification** for stargate — the lifecycle,
ticket frontmatter, reviewer behavior, escalation menu, and commit conventions
that apply to ticket-driven work across features. It is the single source of
truth for the procedure.

The verbatim Constitution principles live in
[`.specify/memory/constitution.md`](../../.specify/memory/constitution.md);
the per-task review loop (round cap and escalation menu) lives in
[`.specify/memory/review-loop.md`](../../.specify/memory/review-loop.md). If
this document conflicts with either, those win — flag the drift and stop.

The skills that drive this workflow (under `.claude/skills/`,
`.opencode/skill/`) are **procedure-only thin wrappers** around this file.
They defer to it on any conflict.

## The unit of work

**One ticket = one focused commit on the feature integration branch; the
feature branch squash-merges to `main` at milestone close.**

- Ticket files live at `specs/NNN-feature/tickets/T-NNN-<slug>.md`, one file
  per ticket, YAML frontmatter (see `ticket-template.md`).
- Branch: the **feature integration branch** (e.g. `001-tor-route`), named
  from the feature directory in `.specify/feature.json`. Per-ticket work
  commits directly to this branch; `run-task.sh` creates the focused commit
  at APPROVE. `main` has no scripts mid-feature, so per-ticket branches off
  `main` are unbuildable; the milestone squash-merge (`run-task.sh <id>
  --merge`) folds the whole feature branch into `main` at milestone close.
- `tasks.md` is the spec-kit plan; it is regenerated by `/speckit-tasks`. The
  `tickets/` directory is **not** regenerated — `scripts/bootstrap-tickets.sh`
  derives it once from tasks.md, then the tickets are maintained independently.
  The `[X]`/`[ ]` markers in tasks.md become a derived view from ticket
  `status:`; never hand-edit them.
- **Tests-first direction is explicit metadata, not prose inference.** An
  implementation ticket declares its Principle-VII tests via
  `tests_first: [T-NNN, ...]`; `scripts/derive-deps.sh` adds those tests to
  the impl's `blocked_by`, and `scripts/lint-ticket.py` rejects a
  privacy-critical impl runnable before its named test. The ambiguous
  `Pairs with` prose signal was removed (T096 / sol-review M6) — it inverted
  tests-first ordering.
- **Never `--amend` a passed commit.** Defects after approval become a new
  ticket (use the `remediates:` lineage field) and a new commit.

## Lifecycle

```
   pending  ──────────────────────────────────────────────┐
      │  ▲                                                │
      │  │ refine after clarity-fail / outline-fail       │
      │  │                                                │
      ▼  │                                                ▼
   in-progress  ──────────→  in-review  ─────────→  done  ──→  (squash-merged into main)
       ▲                         │
       │   REWORK rounds 1..N    │
       └─────────────────────────┘
       (N=2 default; 3 if round_cap: 3)         ▼
                                       escalated  ──→  refine / override / decompose / defer / amend
                                       deferred    ──→  (resume via `reopen` once blocker done)
```

| Status | Meaning |
|---|---|
| `pending` | Drafted, not yet started. May be `blocked_by` other tickets. |
| `in-progress` | Branch exists; developer is implementing. |
| `in-review` | `verify.sh` green; the isolated single-gate reviewer set is pending or complete. |
| `escalated` | Round cap hit, or an immediate-escalation trigger fired. Awaiting user resolution via the menu. |
| `done` | Reviewer returned `APPROVE` (or `OVERRIDE-APPROVE`); commit landed on the branch. Squash-merge into `main` is a separate step. |
| `deferred` | Paused — out-of-scope discovered, blocked on new work, or waiting on a spec amendment. |

## The flow

0. **Pick** — `scripts/next-task.sh` resolves tickets where `status: pending`
   AND every `blocked_by` has `status: done`. Lowest id wins; `--count N`
   limits; `--json` for machine consumers. For the full board across all
   statuses, `scripts/regen-status.sh` regenerates `specs/NNN-feature/STATUS.md`
   from frontmatter (derived; never hand-edit).
1. **Drive** — `scripts/run-task.sh <id>` is the state machine. It performs
   the deterministic phases directly (verify, status transitions, merge) and
   emits structured handoff prompts at the non-deterministic phases (ground,
   implement, review). The caller — a human at the terminal, or an
   external agent driver, or a future `/run` autopilot — reads the prompt,
   does the work, signals ready via a sentinel file, and re-invokes
   `run-task.sh` to advance. Resume-aware: enters at the right phase based on
   ticket `status:`. The script never pushes, never spawns a developer-
   subagent (no portable way to do that from shell), and round/verdict state
   lives under gitignored `target/runs/`.
   - For session-resume across context resets, `scripts/handoff.sh <id>`
     writes a structured handoff under gitignored `specs/<feature>/.handoffs/`
     with the load-bearing state captured and re-verified at write time.
2. **Start** (the run-task `pending` phase) — land on the feature integration
   branch (`run-task.sh` creates it from `main` if absent, checks it out
   otherwise, refuses a dirty tree or an ambiguous ticket match); flip
   `status: in-progress`. Pre-flight:
   - **Ground on the ticket, alone** — read the whole ticket file + every
     cited `spec_refs:` / `decision_refs:` / `constitution_refs:` anchor +
     the relevant contract under `specs/NNN-feature/contracts/`. Verify on
     disk that any module or path named in acceptance resolves. Do NOT pair
     this read with the implement step — that's the "ground before acting"
     doctrine.
   - **Analyze** (`docs/process/analysis.md`, planned): build the property map
     — what must hold · which `verify.sh` gates already catch it · the
     **residue** no gate catches. Required when `privacy_critical: true` OR
     `complexity: high`; a quick pass otherwise. The residue scopes the
     security lane of the review gate and the tests to write.
   - **Clarity pre-flight** — `python3 scripts/lint-ticket.py` runs the
     mechanical subset. A full fresh-context `clarity-reviewer` subagent
     (future) adds the judgment layer; `lint-ticket.py` is the floor.
   - **Plan (high complexity only)** — if `complexity: high`, a fresh-context
     plan-writer drafts an outline sidecar at `specs/.handoffs/T-NNN-OUTLINE.md`
     (gitignored) before any code. `OUTLINE FAILED` → refine the ticket.
3. **Implement** (the run-task `in-progress` phase) — the main conversation
   IS the developer (never a developer-subagent). Surgical changes only,
   within `files_budget`. For `privacy_critical: true` tasks: **tests first**
   (Constitution Principle VII, no AI exception) — the test must exist and be
   failing before the implementation lands. For a new behavior or fix, stage
   the spec-derived test and run `python3 scripts/test-first-evidence.py red
   TNNN -- <test command>` before implementation. After the fix, stage source
   and rerun the identical probe command through the tool with `green`. Stage its
   `specs/<feature>/evidence/TNNN-tests-first.json` record explicitly. The
   driver checks that the record names the task baseline and the current
   implemented source snapshot before review and again before commit. A
   ticket with `test_for` is separately deliverable test-only work; its later
   implementation ticket carries the red/green record. `tests_first` remains
   a directed dependency, not a substitute for the implementation record.
   The reviewer checks that the recorded red output demonstrates the named
   property rather than missing tooling, and that the pre-fix patch contains
   the intended test. For a `test_for` ticket that skips the record, the
   reviewer checks that the diff contains only test work; an implementation
   change under that label is REWORK. Do not put secrets in probe output or
   the staged record.
4. **Verify** (run-task runs this directly before transition to in-review) —
   `scripts/verify.sh` from repo root. **The single green gate.** Fix the
   code, never the test, unless the ticket's §Out-of-scope authorized that
   test change. The implementer does not run it by hand: `run-task.sh`
   runs it as the pre-review gate and again at APPROVE only when the
   executable content changed since the last GREEN run (ticket lifecycle
   fields, `STATUS.md`, evidence, the scorecard and plain Go/Java `//`
   comments do not count; see `code_digest`).
5. **Review** (the run-task `in-review` phase) — emit a handoff for
   `scripts/review-task.sh <id>` — the single gate. ONE invocation, ONE pass:
   the launcher runs one OpenCode GLM reviewer and one Codex Astra reviewer
   concurrently; each covers correctness AND adversarial security/privacy in
   the same pass (there is no second redteam phase). Each receives a
   separately materialized candidate, fresh context and separate temporary/output
   paths. The two native CLI sessions receive no implementation chat or peer
   verdicts. OpenCode uses reviewer permissions; Codex runs without an OS sandbox
   under read-only inspection instructions. Separate copies are not a host security boundary. Reviewers receive the
   source candidate and the driver handoff: diff base, staged candidate,
   ticket, files-vs-budget, verify freshness, §Out-of-scope and prior-round
   verdict on round ≥ 2. They do not receive live run state, peer verdicts or
   implementation chat/rationale.
   The launcher validates reviewer/tool/model/effort/snapshot/round fields,
   imports both reviewer-written verdicts, then writes the set manifest
   last; the caller never transcribes them. Re-invoking run-task.sh requires
   the manifest and every hash/identity before acting (APPROVE → commit;
   APPROVE-WITH-FIXES → APPLY-FIXES
   handoff: caller applies the comment-only FIX ITEMS, re-verifies, touches
   `target/runs/<id>.awf-applied`; source changes invalidate the old snapshot and require
   renewed review in the same round before commit (Constitution VIII);
   REWORK → bump round; ESCALATE → surface the menu). Verdict:
   `APPROVE | APPROVE-WITH-FIXES | REWORK | ESCALATE`; the strongest verdict
   in the set wins and every verdict carries `SUMMARY` and `FINDINGS`.
   The gate binds HEAD, baseline, worktree, index, round and the non-ignored
   source inventory. Changes invalidate all approvals, including changes
   during final verification. Legacy or partial verdict files cannot approve work.
   Every reviewer verdict must copy the handoff's exact `SNAPSHOT` and `ROUND`,
   each once. Missing, duplicate or mismatched identity, a partial set, or a
   delayed response to an older handoff is refused.
6. **Resolve:**

   | Verdict | Action |
   |---|---|
   | `APPROVE` | Commit — the single gate already covered security for privacy-critical tickets. |
   | `APPROVE-WITH-FIXES` | Apply ONLY its comment/doc-only FIX ITEMS; re-`verify`; touch `.awf-applied`; refresh review of the changed snapshot and commit — no round-counter increment. |
   | `REWORK` (round 1) | Address only the named items; re-`verify`; re-review. |
   | `REWORK` (round 2 = cap) / `ESCALATE` | STOP. Surface the menu (below). **You** decide. |

7. **Commit** — `run-task.sh` creates the focused commit on the feature
   branch at APPROVE (one commit per ticket: `Implement <feature>: T-NNN:
   <imperative summary ≤72 chars>` + the §Context paragraph + a
   one `Reviewed-by:` trailer per reviewer recording its role, identity, tool,
   model, effort, actual verdict and round).
   It commits ONLY paths the developer staged during IMPLEMENT — never
   `git add -A` — and refuses to flip `done` if nothing is staged. Flip
   `status: done`.
8. **Merge** — `scripts/run-task.sh <id> --merge` is the **milestone**
   squash-merge: it folds the whole feature integration branch into local
   `main` with a generated milestone message, targets the feature branch by
   name (never guesses from the caller's current branch), refuses a dirty
   tree, and never deletes the feature branch. **Never auto-push**; push is
   the user's call (the outward, irreversible step). Per-ticket push
   (`git push origin <feature-branch>`) is also the user's call, after the
   APPROVE commit lands.

## Escalation menu (the human decides; the agent never picks)

When the round cap is hit, `verify.sh` cannot reach green within budget, or
the reviewer returns `ESCALATE`, present exactly these options and **stop**:

1. **refine** — acceptance criteria were ambiguous or wrong-grained. Rewrite
   the ticket's §Acceptance, then restart from `pending`.
2. **override** — the reviewer was too strict; the code is correct as-is.
   Record one line of *why* under `overrides:`. If the overridden finding was
   security/privacy, append the rationale to `SECURITY-DECISIONS.md`
   (append-only) — no AI exception to Constitution Principle VIII.
3. **decompose** — the ticket is too large to land in the round cap. Split it
   into smaller `T-NNN.a`, `T-NNN.b` children; mark this one `deferred` with
   `deferred_reason: decomposed` and `decomposed_from:` populated on each child.
4. **defer** — blocked on work that does not exist yet. Mark `deferred`, set
   `deferred_on:` and `deferred_reason: blocked-on-new-ticket`; file the
   follow-up.
5. **amend** — the spec or the Constitution itself is wrong. Two weights:
   - **amend-spec** — revise `specs/NNN-feature/spec.md` (and re-run
     `/speckit-plan`'s Constitution Check). Lighter.
   - **amend-constitution** — follow the active Governance section in
     `.specify/memory/constitution.md`. Pre-release session authorization and
     post-release PR/comment rules differ. Any security/privacy/governance-impacting
     amendment requires independent redteam wherever it is located. Finding acceptance
     cannot waive a principle. The maintainer decides an unresolved policy change.

## Adversarial passes (milestone redteam + perf)

Separate from the per-ticket single gate and **blind to rationale**.

- **`stargate-redteam`** — cumulative security/privacy fresh-eyes pass. Sees
  `THREAT-MODEL.md` + the cumulative diff, NOT the design notes or ticket
  bodies. Hunts the gap between Constitution promise and shipped bytes.
  Per-ticket security review is owned by the single gate (both its reviewers
  run the adversarial checklist every pass); this role runs at
  feature boundaries and before release tags against cumulative changes.
  Ticket Blocker/Major findings prevent commit; human acceptance follows the
  existing override process and SECURITY-DECISIONS.md. Milestone findings on
  completed tickets become remediation tickets.
- **Context and capability boundary** — `scripts/review-task.sh` starts exactly
  two native CLI child sessions, one GLM-5.3-Flash at xhigh (provider `max`) and
  one Astra at high, both running the single merged gate in one pass. No Docker
  or replacement containment infrastructure is required. Separate source copies,
  temporary directories and verdict paths avoid accidental interference. Both
  copies are checked against the driver snapshot before and after review.
  Reviewers use the invoking user's existing provider authentication and retain
  same-user host access subject to their tool controls. OpenCode deny maps are
  not an OS sandbox; Codex explicitly runs without one. No host credential, filesystem,
  process or network isolation is claimed. Deterministic native CLI stand-ins
  test orchestration, efforts, source-mutation rejection and complete verdict import.
- **`stargate-perf`** — performance and resource pass. Runs at milestone
  boundaries. Identifies hot-path allocations, blocking-on-event-loop, leaks.

Findings on `done` tickets become **new remediation tickets** with
`remediates: T-NNN` set; the original commit is never amended.

## Evidence and atomic tests-first work (T156)

Use the strictest applicable test category, including privacy-sensitive Docker/scripts.
Preserve the spec-derived falsifier, failing command/result and pre-fix snapshot, then the
passing result and implemented snapshot. Tooling failure alone is not the intended red result.
The durable per-ticket JSON under `specs/<feature>/evidence/` records the task baseline,
pre-fix diff and probe result, and the staged implementation digest and passing result
from the identical probe command. Capture and review reject source differences between
the index and working tree, because Git commits the index while the probe runs against
working files.
`run-task.sh` rejects a missing record or mismatched baseline/source for privacy-critical
implementation work. The hashes bind records to source; they do not establish that a
recorded probe tested the right property. Independent review must make that judgment.
Required unavailable/live checks remain pending; a successful verify with SKIPs is not proof
of their properties. Every review records actual reviewer/tool identity, scope, candidate hash,
coverage and limitations. No unsupported model/expertise claims or fabricated historical evidence.
Normative documentation changes use consistency probes and independent review, not invented
runtime tests. Existing behavior may be covered retrospectively and must be labelled honestly.

`tests_first` names only separately deliverable test tickets that can pass their own green gate.
If a new regression must stay red until its implementation, refine before executing it: put the
regression and fix in one focused implementation ticket, with a required red-before-green
sequence in Acceptance. Mark replaced standalone tickets deferred/decomposed, link their owner,
and replace downstream blockers with that owner. Do not require a done red-only test ticket or
commit disabled/permanently-skipped tests. Record this refinement and preserve scope/review gates.

Before an investigation is marked done, file every required implementation follow-up and add it
to the foundation/milestone closure tickets AND affected consumers. Put this obligation in
Acceptance, not non-binding Notes. If required work is unidentified, the investigation is not done.
A reviewed recommendation does not resolve an implementation finding. Additive graph updates
must remain acyclic; regenerate STATUS after every lifecycle/dependency change.

For an amendment or uncommitted multi-document review, preserve a scoped diff and manifest
hashing all input files (including untracked files). Reviewers bind that exact manifest hash.
Count every touched path toward files_budget, including specs, the ticket and new files;
there is no directory exemption. Before driver review, explicitly stage every intended new
source file so it appears in the diff/snapshot; compare that inventory with the scoped manifest.
T139 enforces this before review and commit: every non-ignored untracked path blocks until
explicitly staged, and the union of worktree/index changed paths counts toward files_budget
(including ticket/spec/docs paths and staged additions). Ignored build output is excluded;
intended source matching an ignore rule must be explicitly force-added before review. Review
hashes cover both staged and working content, HEAD, baseline and round; new source or changed
content invalidates approvals, including during final verification. This also applies to
comment/doc corrections: refreshed review uses the same round, so corrections do not consume
a REWORK round. An approval without a recorded review snapshot cannot authorize commit.
Lifecycle/verdict records are review outputs, not permission to change reviewed source afterward.
A pending amendment becomes completed only through the normal reviewed commit/delivery phase;
recorded approvals do not fabricate a missing commit. The human external review gate in VIII
also binds the released candidate and security-impacting changes since its review.

## Live end-to-end verification (release-cadence; deferred to Phase 5+)

The contract tests under `tests/contract/` prove the **assumed** sidecar /
transport contract. They do **not** re-prove what the contract test layer is
structurally incapable of seeing: real Tor network behaviour, real Mullvad
Browser routing decisions, real DNS resolver behaviour, real packet-level
egress. That gap closes with **live end-to-end runs** at release cadence, not
PR cadence — `T034a` (SC-003 DNS-leak Wireshark measurement),
`T034f` (egress-consensus packet capture against live Tor consensus), and the
release-tag sweeps (`T077`–`T079`) are existing instances of this pattern,
inlined into the spec rather than gathered under a tracker.

When the first vertical slice approaches `done` (Phase 5+), author a living
tracker at `specs/NNN-feature/live-e2e/README.md` that:

- Pulls the release-cadence scenarios into one place.
- Adds a `D-live-N` decisions log (same shape as infochat's
  `docs/plan/live-e2e/README.md`, adapted to stargate's threat model).
- Documents the **preserve / reset** split — for stargate the analog is the
  `dp-snapshot.json` cold-start cache (`data-model.md §1.4`, preserve) vs the
  re-pushed control-plane token generation (reset). The cold-start cache is
  *not* a live-test artefact; the mapping is conceptual.
- Classifies each acceptance scenario as **transport-invisible** (stays in
  contract tests — e.g. SOCKS5 byte sequences, error-template literals,
  proto schema conformance) vs **transport-relevant** (live only — e.g. real
  Tor consensus reachability, real DNS leak surface, real Mullvad Browser
  proxy decisions). The Constitution's Principle I/III properties are
  paradigmatically transport-invisible at the unit-test layer and
  transport-relevant at the live layer.

**Targeting principle** (the load-bearing rule): a live run does **not**
re-prove what `tests/contract/` already covers. It proves ONLY the things the
contract test layer cannot, because the contract test against a real Tor
sidecar in a container still encodes the *assumed* sidecar behaviour; only a
real-network run exercises the *real* one. Per-transport risk does not
transfer — Tor live-test findings say nothing about I2P or Nym; each route
gets its own live verification when its feature ships.

Until Phase 5, leave this section as a forward reference — don't build the
tracker ahead of the substrate.

## Autonomous runs

The green path carries no human decision — each gate (`verify.sh` and the
two isolated single-gate reviewer contexts) is an *independent* check, not
the agent grading itself. So a clean run executes
**unattended**: the autopilot drives start → implement → verify → review →
commit-on-feature, stopping on
**bright-line conditions**:

- **Front** — analyze finds acceptance blank or diverges from ground truth, or
  clarity `FAIL`.
- **Scope** — `files_budget` would be exceeded.
- **Build** — `verify.sh` not green after addressing a rework round.
- **Review** — REWORK round cap or `ESCALATE`.
- **Redteam** — ESCALATE or REWORK at the shared round cap; invalid verdicts
  cannot authorize a commit.

**Push always stays manual.** A local merge is revertible (`git revert
<sha>`); a push is outward and irreversible — keeping it manual is what makes
auto-merge safe.

Every ticket — `privacy_critical` or not — passes the same single gate
before commit on the green path; the privacy flag sharpens the reviewers'
security lane, it does not add a second dispatch. **No separate autonomy
dial** — the flag is the dial, the residue map is its input.

The `/run` skill follows driver handoffs through local completion. Push and
milestone merge require the user's authorization; the skill does not add an
independent commit or push step.

## Pure-doc commits (no ticket)

| Prefix | Scope (no code change) |
|---|---|
| `docs:` | `*.md` under `docs/`, `specs/`, root docs (`THREAT-MODEL.md`, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`) |
| `chore:` | Tooling: `.claude/`, `.opencode/`, `scripts/`, `.githooks/`, `.gitignore`, `.gitattributes` |
| `process:` | This directory (`docs/process/`) and the procedure itself |

Any commit touching production code (`data-plane/**`, `control-plane/**`,
`extension/**`, `proto/**`, `compose/**`, `sidecars/**`, `tests/**`) is a
ticket and uses `T-NNN:`. `git log --grep '^T[0-9]'` enumerates ticketed work
cleanly.

When in doubt, default to the ticket flow. The cost of an unnecessary ticket
is lower than the cost of an unreviewed code change slipping through under a
`docs:` prefix.

## What is NOT in this workflow

- **No automated push.** The user reviews and pushes.
- **No automated PR creation** until CI is wired (planned: `.github/workflows/`).
- **No CI mirror yet.** `verify.sh` IS the gate; a CI workflow that runs it on
  every push is the planned mirror.
- **No external tracker.** GitHub Issues is fine for *user-facing* bug reports
  later; the ticket file is the dev-facing source of truth.

## Process doctrine — deletion over addition

When a check in this workflow produces repeated false positives (≥3), the
default response is to **delete or narrow the check**, not to add rules around
it. A one-off failure is evidence to fix the ticket; a *pattern* is evidence
the check is wrong. Don't patch a one-off into a permanent rule.

Process surface grows easily and shrinks only deliberately. Adopted from an
external team's hard-won AI-assisted workflow; adapted to stargate's
Constitution + spec-kit context.
