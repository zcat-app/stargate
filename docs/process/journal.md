# Process & workflow decision journal

Lightweight, append-only history of process/workflow decisions — the small
problem→decision pairs that aren't worth amending the Constitution or the
review-loop doc, but shouldn't vanish. Oldest-first. Each entry rides along
in the commit that carried the decision.

This is the tier below `.specify/memory/constitution.md` (binding principles)
and `.specify/memory/review-loop.md` (per-task loop mechanics). When a
journal entry accumulates enough weight to become a rule, it gets promoted
upward; when a rule turns out to be wrong, it gets demoted or deleted here
first (deletion over addition — `workflow.md §"Process doctrine"`).

Spec/design decisions live elsewhere (per-feature under `specs/NNN-feature/`);
this file is for **how-we-work** decisions.

## 2026-07-04 — [process] Adopt per-file ticket model over in-place markers

**Problem:** spec-kit's `tasks.md` is regenerated by `/speckit-tasks`; per-task
lifecycle state cannot live in it without being overwritten. Two options
were on the table: (a) per-task files with YAML frontmatter (infochat/zecsite
model — 547+ done tickets on infochat prove it scales), or (b) in-place
HTML-comment markers in tasks.md. The in-place option is a dead end: it
can't carry per-task lifecycle, lineage (`decomposed_from`, `remediates`),
or STATUS regen, and it's a maintenance dead weight once parallel worktrees
or a `/run` autopilot are wanted.

**Decision:** Option (a) — per-file tickets at
`specs/NNN-feature/tickets/T-NNN-*.md`, generated once from tasks.md via
`scripts/bootstrap-tickets.sh` and maintained independently. tasks.md
remains the spec-kit plan; the `[X]`/`[ ]` markers become a derived view
from ticket `status:`. Mirrors infochat's `docs/plan/` vs
`docs/plan/m1/tickets/` split and zecsite's `roadmap.md` vs `tickets/`
split.

**Why it won:** in-place markers can't carry the lifecycle, lineage, or
STATUS board. The evidence from infochat (547 done) and zecsite (lighter
variant) is one-sided.

**Links:** `scripts/bootstrap-tickets.sh` · `docs/process/ticket-template.md`
· `docs/process/workflow.md`

## 2026-07-04 — [process] Skills are procedure-only thin wrappers; procedure lives in shell + markdown

**Problem:** stargate's workflow needs to work across opencode, Claude Code,
zcode, and any future agent tool. Authoring the workflow as Claude-specific
skills (`.claude/skills/`) couples it to one tool's slash-command format
and frontmatter shape; opencode and zcode see none of it.

**Decision:** The procedure lives in shell scripts
(`scripts/run-task.sh`, `scripts/verify.sh`, `scripts/next-task.sh`, etc.)
and markdown docs (`docs/process/workflow.md`, `review-loop.md`,
`ticket-template.md`). The skills (`.claude/skills/run/SKILL.md`,
`.opencode/skills/run/SKILL.md`) are deliberately thin wrappers that defer
to those sources on any conflict. Mirrors zecsite's "skill is procedure
only" doctrine and infochat's "docs/process/workflow.md is the source of
truth" pattern.

**Why it won:** the workflow IS tool-agnostic by construction. Adding a
new tool means writing a thin skill wrapper, not porting the procedure.

**Links:** `docs/process/workflow.md` · `.claude/skills/run/SKILL.md` ·
`.opencode/skills/run/SKILL.md` · `AGENTS.md`

## 2026-07-04 — [process] opencode as primary agent CLI; dispatcher pattern for swappability

**Problem:** the CI workflow (`.github/workflows/agent-task.yml`) needs an
"agent CLI" — a program that takes a prompt and does the LLM-driven work
emitted by `run-task.sh`. Three candidates: opencode (`opencode run`),
Claude Code (`claude -p`), or a custom runner. Hardcoding any one couples
the workflow to that tool's CLI quirks (auth, flags, output format).

**Decision:** opencode is stargate's primary agent CLI. The dispatcher
(`scripts/agent-cli.sh`) isolates the per-tool quirks in adapter files
under `scripts/agent-cli/<tool>.sh`; the workflow and any other caller go
through the single entry point. Switching to Claude or another tool is
one env var (`AGENT_CLI=claude`) and one adapter file. Verified the
opencode invocation against the official CLI docs (`opencode run --auto
--dir <workdir> [--agent <name>] [--model <p/m>] <prompt>`); Claude
adapter exists as a stub.

**Why it won:** the swappability is real, not theoretical (the Claude
adapter dispatches today). The dispatcher contract is tiny — one shell
function, six env vars, two exit codes — so adding an adapter is a 20-line
file. The user explicitly chose opencode as primary; the stub for Claude
exists so experimentation is possible without forking the dispatcher.

**Links:** `scripts/agent-cli.sh` · `scripts/agent-cli/opencode.sh` ·
`scripts/agent-cli/claude.sh` · `scripts/agent-cli/README.md` ·
`.github/workflows/agent-task.yml`

## 2026-07-04 — [process] Adopt Error Prone + NullAway for the control plane (decision D48 port)

**Problem:** stargate's data plane gets `gofmt + go vet + staticcheck +
gosec` (verify.sh gate 2). The control plane gets no static-analysis
equivalent — just `mvn verify`, which is runtime tests only. The "validate
at edges, trust inside" doctrine (CONTRIBUTING.md) has no mechanical
enforcement today; it relies on the reviewer noticing.

**Decision:** Port infochat's decision D48 (NullAway + Error Prone) to
stargate. The Maven parent POM wires both as compile-time annotation
processors with `NullAway:ERROR` active; `app.zcat.stargate` packages are
`@NonNull` by default; genuinely-nullable edge types declare `@Nullable`
via JSpecify (not JetBrains — type-use semantics). Drafted as ticket T081;
blocked_by T003 (the Maven reactor). Test-source onboarding is per-module
in follow-up tickets (T081a/b/c).

**Why it won:** maps directly to the Constitution's edge-vs-inside
doctrine; closes a real gap (the Java side had no static analysis); feeds
the analyze gate (zecsite residue pattern) by moving nullness-violation
properties from "residue" into "gated by verify.sh fail-closed".
Precedent: infochat D48 is the same config with the same doctrine,
working at scale.

**Load-bearing gotchas ported from infochat:** (a) the
`-Xplugin:ErrorProne` and `-XepOpt:NullAway:...` flags MUST share a single
`<arg>` element — splitting them silently disables NullAway
(green-but-not-enforced); (b) `<fork>true</fork>` is required for javac
reflective access; (c) JSpecify 1.0.0 is the annotation source (type-use
semantics), not JSR-305 or JetBrains.

**Links:** `specs/001-tor-route/tickets/T081-*.md` ·
infochat `docs/process/engineering-rules-verbatim.md §7a`

## 2026-07-04 — [process] Defer live-e2e tracker to Phase 5; release-cadence tests stay inline for now

**Problem:** infochat's `docs/plan/live-e2e/README.md` (408 lines) is a
mature pattern for verifying what contract tests cannot — real-transport
behaviour, real LLM/embedding quality, real operator UX. stargate's
release-cadence tests (T034a SC-003 DNS-leak, T034f egress consensus) are
already instances of this pattern, but inlined into the spec rather than
gathered under a tracker. Should stargate build the tracker now?

**Decision:** No — defer to Phase 5 of 001-tor-route. stargate is in Phase
2 of 7; the substrate (compose file, sidecar, control plane) doesn't exist
yet. The release-cadence tests already encode the targeting principle
inline. Added a forward-reference section to `docs/process/workflow.md`
("Live end-to-end verification") capturing the pattern's shape, the
preserve/reset mapping to `dp-snapshot.json`, and the transport-invisible
vs transport-relevant classification, so it's not forgotten.

**Why it won:** building the tracker ahead of the substrate is structure
ahead of need (zesite's anti-pattern). The posture (release-cadence live
tests inline in the spec) is already in place via T034a/T034f/T077–T079;
no urgent gap.

**Links:** `docs/process/workflow.md §"Live end-to-end verification"` ·
infochat `docs/plan/live-e2e/README.md` (the precedent)

## 2026-07-04 — [process] HTML docs structure with honest-placeholder approach

**Problem:** user wants navigable HTML documentation (markdown is hard to
navigate for humans). The proxy itself is not yet shipped, so most
end-user docs would be fiction if written now. The Constitution's "Open
and Auditable" principle cuts against aspirational docs that read like
shipped features.

**Decision:** Build the full HTML structure (index + 5 sections + diagrams
gallery) with **honest-placeholder banners per page**. Pages documenting
real things today (tech, developer, diagrams) are substantive; pages
documenting unbuilt features (user-guide, advanced, admin) carry yellow
"not yet shipped" banners, outline what they WILL cover, and link to the
authoritative source docs (Constitution, THREAT-MODEL.md, specs/) for the
substantive content that IS decided. Pure HTML + inline SVG + ~30 lines
vanilla JS; no external dependencies; opens from `file://`.

**Why it won:** structure-ahead-of-content with explicit banners beats
either (a) no docs at all (no navigation surface), or (b) fully-written
fiction (drifts from reality, violates Open and Auditable). The banner
discipline means each section graduates to verified-true incrementally as
the feature ships.

**Links:** `docs/html/*.html` · `docs/html/style.css`

## 2026-07-04 — [process] future-work.md captures FW-1 (blocklist) + FW-2 (search-fanout)

**Problem:** Two feature ideas surfaced mid-session (malicious-URL
blocklist in the extension; multi-engine search-fanout as a sibling
service). Forgetting them means re-evaluating from scratch later;
recording them as tickets implies commitment.

**Decision:** New `docs/future-work.md` as a memory aid (not a roadmap).
Each entry carries: the idea, where it fits architecturally (with
Constitution-fit reasoning), constraints any future spec must honour,
smells to surface in the spec, and a "do not start before" gate. When an
item promotes to a real spec, its full entry collapses to a one-line
pointer. FW-1 fits in the extension (NOT the proxy — violates Principle
I); FW-2 fits as a sibling service consuming stargate's SOCKS5 port (NOT
in stargate — violates "no outbound from Stargate" doctrine).

**Why it won:** captures the architectural reasoning (which is expensive
to re-derive) without committing to implementation. The "Items considered
and rejected" section (currently empty) is also part of the contract —
rejected ideas get recorded so they don't get re-evaluated.

**Links:** `docs/future-work.md`
