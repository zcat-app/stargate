Advanced guide

Status: partial. Deployment profiles and the per-route privacy properties are documented in THREAT-MODEL.md and the architecture spec; the per-site routing rules and other advanced features are v1 scope but not yet wired into the extension. What follows is the outline plus the substantive pieces that are decided.

Deployment profiles

Three Docker Compose profiles, switched by topology. The proxy refuses to bind a non-loopback interface without a corresponding tunnel sidecar (this is enforced in code, not config — see data-plane/internal/bind once ticket T013 lands).

ProfileUse caseTopology
local Personal use on a workstation. Browser, data plane, sidecar all on the same host. Proxy binds 127.0.0.1 only.
lan Household, multiple devices. WireGuard sidecar on the LAN carries per-device traffic to the data plane.
vps Always-on egress from a remote host. Devices tunnel to a VPS via WireGuard or Tailscale; the data plane runs on the VPS.

See the deployment-profiles diagrams for the visual topologies of each.

Routes and what each protects against

Stargate supports four routes. The browser extension picks one per request. What each route actually defends against is documented in THREAT-MODEL.md; the summary below is the short version.

Route Network Defends against Does NOT defend against
Tor Tor overlay Local network observer seeing the destination; clearnet exit observer seeing the source IP (for clearnet-via-Tor). Global passive adversary correlating timing/volume; malicious exit node reading or modifying unencrypted clearnet traffic; the Tor network's own biases.
I2P I2P overlay Similar to Tor for .i2p destinations; distributed by design. Cross-overlay leakage; the I2P network's own biases.
Nym Nym mixnet Stronger metadata resistance than Tor via Sphinx packet mixing and cover traffic (when enabled). Performance — mixnet latency is higher; Nym's own threat model and operator set.
Direct Clearnet, no overlay Nothing on the network side. Used for sites that block anonymous exits or where anonymity is not the goal. Everything — your IP is exposed. Use deliberately.

The full per-route threat model — including the threat-model entries for malicious sidecars, DNS leak surface, and the difference between local, lan, and vps profiles per route — lives in THREAT-MODEL.md. This page summarises; that file is the contract.

What is NOT decided yet (placeholders for v1+)

Per-site routing rules

The extension will support persistent rules: "always use Tor for .onion", "always use Direct for bank.example.com". The rule schema, the persistence format, and the UI are v1 scope but not yet specced in detail. Tracked in specs/001-tor-route/spec.md.

Custom SOCKS5 routing

Power users may want to point non-browser applications (curl, git, etc.) at the data plane's SOCKS5 port directly, with route selection via the SOCKS5 username. Whether the v1 extension handles this or it stays a developer-only path is an open question.

Bridge / pluggable-transport configuration

Tor bridges are supported in v1, toggleable, default off. The extension exposes the toggle; the rendered torrc template includes the bridge lines when enabled. Per-ticket tracking: T029–T032 (the torrc contract tests).

What is explicitly out of scope (v1)

  • Cover traffic. The data plane generates no cover traffic (Constitution Principle I). Nym's own cover-traffic mechanism applies when the Nym route is selected, but Stargate itself does not add any.
  • Per-request logging. The data plane emits no per-request log line at any granularity. Aggregate counters only, at ≥1-hour bucket resolution (FR-008). This is enforced by the contract tests T025a / T025c.
  • Local DNS resolution. The data plane does not resolve DNS names. SOCKS5h only; the sidecar does the resolution. This is enforced by T034 (DNS leak test).
