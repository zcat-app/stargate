Administrator guide

Status: placeholder. Most admin operations (observability stack, dashboard UI, automated upgrade flow) are post-v1. The principles and constraints below are decided; the tooling to execute them is not yet built.

Principles that bind admin operations

Two Constitution principles shape what an admin can and cannot do, even once the tooling lands:

Principle III — no outbound except routed request
The proxy itself makes no outbound connections for status, monitoring, telemetry, update checks, or notifications. All observability is local-only in v1. There is no "phone home" path; the admin reads metrics off the local control plane, not a cloud dashboard.
Principle IV — every external component is digest-pinned
Sidecar images, base images, build tools — every external artefact the proxy depends on is pinned by sha256 digest, not tag. Upgrades are explicit, audited, and reproducible. There is no latest tag anywhere in the deployment graph.
Principle VI — Open and Auditable
Every admin action lands in the append-only audit log (audit_log table; data-model §4). The audit log is row-level append-only — it cannot be silently truncated; only the owner role can TRUNCATE it.

Upgrade procedure

Target flow:

  1. Pin the new release's image digests in compose/env/<profile>.env.
  2. scripts/stargate update pulls the new digests, verifies them against the release manifest, and stages a parallel-stack bring-up.
  3. Healthcheck on the new stack; if green, swap the routing and drain the old one. If red, refuse and surface the failing check.
  4. The old stack's state volume is preserved across the swap (token generation, audit log, snapshot cache); no re-enrollment needed.

Sidecar upgrades specifically (Tor, I2P, Nym) require additional care: the new sidecar image's signing-key fingerprint is verified at build time against sidecars/<route>/apt-key.fingerprint (ticket T014 for Tor; equivalent contracts for I2P/Nym land with those features).

Observability

What lands in v1:

  • The control plane exposes a local GET /healthz for the compose healthcheck (ticket T040). Reachable only inside the compose-internal network; no host port mapping.
  • The data plane exposes a GetStatus gRPC RPC for aggregate counters (per-route request count, byte count, hour bucket). Used by the test harness in v1; the admin UI consumes it post-v1.
  • Per-request data is never exposed. Aggregate counters only.

What is explicitly NOT in v1:

  • Prometheus exporter (no outbound from Stargate; the local-only constraint applies).
  • Distributed tracing.
  • Per-user, per-host, or per-destination metrics.

Backup and restore

The state worth preserving is small in v1:

  • Control plane: SQLite database (audit log, enrolled devices, settings). Filesystem-level backup of the volume.
  • Data plane: dp-snapshot.json — the cold-start cache of the current token generation. Without it, the data plane cold-starts DISABLED and waits for the control plane to push a fresh generation (Principle II survival).
  • Identity: ed25519 plane keys (cp.priv, dp.priv, cp.pub, dp.pub) in the stargate-keys volume. Losing these requires re-enrollment of every enrolled device.

Restore procedure lands post-v1; target is a one-shot scripts/stargate import from a backup archive.

Security advisories

Reporting and disclosure are documented in CONTRIBUTING.md §"Reporting security issues":

Do not open a public GitHub issue for security bugs. Report privately via GitHub Security Advisories. The maintainer aims to acknowledge within 7 days. Coordinated disclosure is the default. If a privacy property documented in THREAT-MODEL.md does not hold, that is a security issue.

Accepted Blocker/Major findings get a rationale entry in SECURITY-DECISIONS.md (append-only) — the audit trail of which findings were accepted rather than fixed and why. This is itself auditable.

What is explicitly out of scope for admin tooling

  • Remote administration over the network. The admin UI is local-only in v1; remote admin (e.g. managing a VPS-deployed instance from a laptop) requires a tunnel (WireGuard/Tailscale), not a Stargate-side feature.
  • Automatic security updates. Sidecar version bumps follow the same digest-pin process as Quarkus LTS bumps (CONTRIBUTING.md §Development environment); they are never silent or automatic.
  • Multi-tenant administration. v1 is family-shareable; per-user admin roles land in a later feature.
