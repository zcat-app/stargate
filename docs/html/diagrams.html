Diagrams — visual mental models

An experiment: do these visuals aid understanding more than the prose in THREAT-MODEL.md, AGENTS.md, and docs/process/workflow.md? If yes, the keepers get embedded into the other HTML pages; the rest get pruned. Pure inline SVG + CSS animations + vanilla JS, no external dependencies, opens from file://.

These diagrams depict the v1 target architecture, not what is shipped today. The proxy itself is still in development. The diagrams are useful as mental models now; they will be useful as references when v1 lands. Components in green (control plane, agent workflow) are real today; components in orange/purple (data plane, sidecars) are unbuilt.

1. Two-plane architecture

The central mental model. Two processes, distinct lifecycles, gRPC over Unix socket between them. The browser extension is where route choice happens; the data plane is a dumb router (Constitution Principle I).

Reading the diagram: blue is browser-side, orange is the privacy-critical data plane, green is the admin control plane, purple is the sidecar. Animated blue dashed lines are bytes flowing on the request path. The green dashed line is the inter-plane control channel — the data plane keeps routing if this channel drops (Constitution Principle II).

2. Deployment profiles (tabbed)

Three Docker Compose profiles, switched by topology. The proxy refuses to bind a non-loopback interface without a corresponding tunnel sidecar.

local — single user, loopback only. The default for personal use on a workstation. Browser, data plane, and sidecar all run on the same host; the proxy binds only 127.0.0.1.

lan — household, multiple devices. A WireGuard sidecar on the LAN carries traffic from each device to the data plane.

vps — remote-host deployment. Devices tunnel to a VPS via WireGuard or Tailscale; the data plane runs on the VPS. Used when the workstation shouldn't be the always-on egress point.

3. Request flow walkthrough (animated)

Step through a single request — typing a URL into the browser, ending with bytes returning from the upstream. Each step highlights what each component sees and what it does NOT see (the privacy-critical boundary).

Step 1 of 7: User types a URL

4. Ticket lifecycle state machine

The workflow from docs/process/workflow.md, visualized. Green is the happy path; red borders are bright-line stops that hand back to the human; yellow is a rework round within the cap.

Reading the diagram: the green path runs unattended under /run or the CI agent-task workflow. Red edges are the bright-line stops — the agent never self-overrides these; the human decides via the five-way menu (refine / override / decompose / defer / amend). The yellow node is a rework round; the cap defaults to 2 (3 for high-risk tickets).

5. The /run loop (CI or local)

How scripts/run-task.sh and scripts/agent-cli.sh hand off between deterministic phases and LLM-driven phases. The deterministic phases the script does itself; the LLM phases it emits as handoff prompts and the agent-CLI adapter picks up.

Why a dispatcher: the LLM CLI (opencode, Claude Code, whatever) is the only piece that's tool-specific. Everything else — the state machine, the gates, the bright-line stops, the PR-opening — is tool-agnostic and lives in shell. Swapping CLI is one env var (AGENT_CLI=claude) and one adapter file.
