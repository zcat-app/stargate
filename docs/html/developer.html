The ticket-driven workflow

Every non-trivial change is spec-driven and ticket-driven. The procedure lives in docs/process/workflow.md; the lifecycle is summarised in the state-machine diagram; the loop driver is scripts/run-task.sh.

  1. Spec: /speckit-specify → specs/NNN-feature/spec.md.
  2. Plan: /speckit-plan → plan.md (must include a Constitution Check).
  3. Tasks: /speckit-tasks → tasks.md (the spec-kit plan; regenerated).
  4. Tickets: scripts/bootstrap-tickets.sh → specs/NNN-feature/tickets/T-NNN-*.md (executable work units with lifecycle state; not overwritten by /speckit-tasks).
  5. Drive: scripts/next-task.sh resolves the runnable set; scripts/run-task.sh <id> drives one ticket through start → implement → verify → review → commit.

Each ticket file carries YAML frontmatter (docs/process/ticket-template.md is the schema). The load-bearing fields:

FieldPurpose
idStable ticket id (T015, T012a, ...).
statusLifecycle state (pending → in-progress → in-review → done; or escalated / deferred).
blocked_byList of ticket ids that must be done before this can start.
privacy_criticalThe autonomy dial. true → tests-first mandatory (Principle VII); stargate-redteam runs before commit; even green verify is not sufficient to auto-commit. false → standard review path; autonomy OK on green verify.
files_budgetNumeric upper bound on files the diff may touch.
round_capDefault 2 rework rounds; 3 only for complexity: high or risk: high.
spec_refs, constitution_refsAnchors into the spec / Constitution. Cite, don't restate.

The scripts/ reference

ScriptPurpose
verify.sh The single green gate. Phase-aware: each gate self-detects whether it has anything to run and SKIPs when code doesn't exist yet. Run before any review/commit.
bootstrap-tickets.sh <feature> One-shot generator: tasks.md → tickets/T-NNN-*.md. Idempotent with --force.
derive-deps.sh Tighten blocked_by lists from tasks.md prose ("Depends on T-NNN", "Pairs with", etc.) and phase ordering.
next-task.sh Resolve runnable tickets. --json for machine consumers, --count N to limit.
lint-ticket.py Author-time mechanical checks on ticket frontmatter.
regen-status.sh Regenerate STATUS.md from ticket frontmatter (derived; never hand-edit).
handoff.sh <id> Write a structured cross-session handoff under gitignored specs/<feature>/.handoffs/.
run-task.sh <id> The loop driver. State machine: drives deterministic phases (verify, status, merge) directly; emits handoff prompts at non-deterministic phases (ground, implement, codereview). --merge performs the squash-merge.
sync-agents.sh Regenerate .opencode/agent/*.md from .claude/agents/ (the canonical source).
agent-cli.sh Pluggable dispatcher for LLM CLIs. AGENT_CLI=opencode (default) or claude or any custom adapter under scripts/agent-cli/<name>.sh.
ground-check.sh External-pin grounding (offline by default; STARGATE_GROUND_ONLINE=1 deepens to digest resolution + EOL checks).
regen-proto.sh Regenerate gRPC stubs from proto/stargate/v1/*.proto deterministically.

Agent setup

Stargate is tool-agnostic. Three entry points are wired:

opencode (primary)

  1. Reads AGENTS.md automatically on session start.
  2. Loads permission rules from opencode.json.
  3. Sees the agent mirrors at .opencode/agent/*.md (regenerate with scripts/sync-agents.sh after editing .claude/agents/).
  4. Sees the run skill at .opencode/skills/run/SKILL.md — type /run T015 to drive a ticket.

Claude Code

  1. Reads CLAUDE.md (thin pointer to AGENTS.md).
  2. Loads .claude/settings.local.json permission allow-list.
  3. Sees the canonical agents at .claude/agents/: stargate-codereview, stargate-redteam, stargate-perf.
  4. Sees the run skill at .claude/skills/run/SKILL.md — type /run T015 to drive a ticket.

zcode / others

  1. Read AGENTS.md + the authoritative sources it cites.
  2. Use scripts/* directly — the workflow is shell-backed and tool-agnostic.

The /run autopilot

The /run <T-NNN> skill (in both .claude/skills/run/ and .opencode/skills/run/) is a thin wrapper around scripts/run-task.sh. It removes the per-phase human rubber-stamp that the shell script's sentinel-file mechanism asks for. On the green path it drives start → implement → verify → codereview → commit unattended; on a bright-line stop it surfaces to the user.

See the /run loop diagram for the dispatch flow between run-task.sh (deterministic) and agent-cli.sh (LLM-driven).

Bright-line stops (the agent never self-overrides these):

  • Clarity FAIL — lint-ticket.py returns non-zero, or privacy_critical: true with §Analysis unfilled.
  • Scope — files_budget about to be exceeded.
  • Build — scripts/verify.sh not green after a rework round.
  • Review — REWORK round cap hit, or ESCALATE verdict.
  • Redteam — FINDINGS from stargate-redteam (privacy-critical tickets only).
  • Must-shrink — a rework round grew files+added+removed simultaneously without a citable mandate.

CI

Two GitHub workflows under .github/workflows/:

verify.yml
Runs on every push and PR. Two jobs: (a) scripts/verify.sh with full toolchain installed; (b) lint-ticket.py across every ticket file + STATUS.md drift check (regen + diff against committed).
agent-task.yml
Triggered by /agent T-NNN issue/PR comments from collaborators with write access, or by manual workflow_dispatch. Checks out a fresh branch, drives run-task.sh in a loop, feeds each emitted prompt to the configured agent-CLI adapter (opencode by default; claude as a stub). Always opens a PR with the partial state and the emitted handoff, regardless of whether the run succeeded or stopped at a bright line.

Working doctrine (from CONTRIBUTING.md)

  • Constitution is authoritative. Re-read it before privacy-critical work.
  • Tests-first for privacy-critical paths (DNS, routing, headers, auth, sidecar contracts) — Constitution Principle VII, no AI exception. Tests are derived from the spec, then implementation is driven to satisfy them.
  • Falsify before publishing. Every claim is a hypothesis. Name what would make it false and check that — re-confirming supporting evidence is confirmation, not verification.
  • Surgical changes only. Every changed line traces to an acceptance criterion, the explicit request, or an orphan your own change created. No drive-by edits.
  • Ground before acting. Read the whole task and verify state on disk before batching edits or running a build that depends on it.
  • No defensive code inside trust boundaries. Validate at system edges (external input, config parsing, deserialization, IPC, file I/O); inside those boundaries, internal-to-internal calls are trusted.
  • No outbound network connections from Stargate except those a request explicitly routes through.
  • No secrets in prompts.

Where to start as a new contributor

  1. Read AGENTS.md — it's the canonical entry-point and it points at everything else.
  2. Re-read .specify/memory/constitution.md before any privacy-critical work.
  3. Run bash scripts/regen-status.sh to see what's runnable.
  4. Run bash scripts/next-task.sh --count 5 to see the lowest-id runnable tickets.
  5. Pick one, run bash scripts/run-task.sh <id> (or /run <id> in your agent of choice).
  6. Run bash scripts/verify.sh before any review/commit.
