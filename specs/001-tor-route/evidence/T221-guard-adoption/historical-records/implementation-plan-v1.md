## Contract

CLI: `check POLICY SHA256 ACTION`, and `run POLICY SHA256 ACTION [--driver PATH -- ORIGINAL_ARGS...]`. Check is read-only, validates all preconditions, and never launches or creates state. Run does the same admission plus serialized journal accounting before spawn. Human/driver output contains a concise reason; blocked/invalid admission exits 78, exhausted/uncertain state also 78; a command timeout exits 124; nonzero child remains failure. No arbitrary caller-supplied command or auto-retry.

Policy is exact raw-byte SHA-256 pinned by caller, strict closed JSON schema (no duplicate keys, unknown fields, booleans-as-numbers, NaN, empty lists masquerading as approval, symlinks/nonregular inputs). It names schema version, run_id, absolute journal_path, absolute deadline epoch seconds, positive maximum attempts and cumulative maximum failed attempts (<=3), exact current phase, pinned plan file, exactly two review descriptors (Astra/high and Luna/high; requested/observable roles only), pinned candidate files, and named actions. Each action has its required phase, `enabled`, nonempty `blocked_reason` when disabled, exact argv (absolute executable), absolute cwd, exact environment object, positive timeout_seconds. Action phase must equal policy phase; disabled action cannot run. A published T218 profile must contain only disabled implementation actions with the unresolved completion-contract reason, not a fake source approval. Generic test fixtures may exercise enabled actions.

Review descriptors pin an actual structured JSON report and require exact role/model/effort, APPROVE verdict, and the exact policy plan SHA256; each reviewer writes their own report. There must be one `gpt-6-astra`/high and one `gpt-6-luna`/high with distinct report paths. Root does not transcribe negative verdicts into approval. Plan review is not source approval; the guard only validates the explicitly named gate. Review reports use schema `task-run-guard-review-v1`, fields role, model, effort, verdict, plan_sha256; optional findings list. JSON itself is not backend identity attestation.

Each pinned file descriptor has exact absolute path, SHA256 and integer mode; verify regular no-symlink path, matching bytes and mode. Policy, plan, reviews, candidates and executable inputs are trusted root-pinned configuration outside the child write scope. Guard checks pins before dispatch and after execution, before returning success. An intentional code-writing action can omit writable paths from the postcondition ONLY if such a distinction is explicitly added to this plan and approved; this version supports commands whose pinned inputs remain unchanged. It is sufficient for driver handoffs, tests and reviewed read-only CLI phases; it does not itself authorize arbitrary implementer writes or establish filesystem containment. Child commands can write outputs in their approved command scope.

Driver hook additionally requires exact match between policy action argv and `/usr/bin/bash`, resolved driver path, original arguments; it cannot execute a different ticket/action through the hook. Guard strips the three hook variables from exact child environment even if supplied. Executable and script command inputs must be included in pins. No broad-test command is included in the session policy. All commands are an exact approved allowlist: no CLI argument to replace/append commands or override policy/budgets.

Persistent state: one no-follow regular append-only JSONL journal, flock held nonblocking for admission through completion (second writer refuses). First record fixes run_id, deadline, maximum attempts/failures. Later policy revisions can change candidate pins, action list and phase but cannot reset that fixed identity/budget. Journal records admitted attempts BEFORE spawn and results afterward, with monotonically sequential attempt number. Any dangling attempt, malformed/truncated record, unknown record, changed immutable metadata, invalid result or cap reached refuses future launches. Only an observed nonzero child increments failed count, but timeout/interruption/unknown completion is a sticky stop. All attempted launches count, including failed spawn. No reset command; renamed policy with same journal cannot evade cap. Missing/deleted/rewritten journal by an unrestricted same-UID operator is outside the guard's security boundary and must be documented, not called tamperproof. Guard never rewrites/deletes failed evidence. Bound input/journal sizes (e.g. policy/reviews <=1MiB, <=1000 attempts) and refuse before unbounded allocation; pin candidate hashing streams.

Time: absolute session deadline admission and per-command timeout limited to remaining wall budget. After start use monotonic elapsed time (original budget cannot be extended by a backward wall-clock jump). Run child in its own process group; inherit output streams (no pipe-EOF wait or unbounded guard output buffer). At timeout/interruption terminate owned process group, bounded TERM grace <=0.25s, then KILL, bounded exact-child reap <=1s; record sticky uncertainty if exact child cannot be reaped. Even successful leader exit requires no remaining process-group members; otherwise terminate and record sticky stop. Never infer absence of escaped descendants or daemon work. Spawn/hash/open/flock/write/close and kernel calls cannot be proven interruptible by this Python guard; no hard realtime or T218 lifecycle guarantee follows. This guard is for harmless/source workflow commands, never native protected-policy commands. External CLI process timeouts are enforceable best effort for ordinary schedulable processes; arbitrary blocked kernel/escaped process containment is not claimed.
