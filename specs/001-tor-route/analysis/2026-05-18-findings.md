**D1 — Constitution III: WebRTC scope and DoT absence.**
Constitution III mandates "DNS-over-HTTPS **and DNS-over-TLS** are disabled; WebRTC
**is disabled**; HTTP/3 / QUIC is disabled" for non-Direct routes. FR-004,
research §10, and T034b cover **DoH only (DoT missing)** and **WebRTC restricted
to `disable_non_proxied_udp`** (which only blocks WebRTC's non-proxied UDP
traffic; WebRTC over the proxy still works — that is *not* "disabled"). Two
distinct gaps against a non-negotiable principle.

**Recommendation**: Either
- (a) amend constitution III via the governance flow (PR + 7-day comment + redteam
  pass, per constitution §Governance, since Principle III is privacy-critical) to
  soften "WebRTC is disabled" → "WebRTC leak paths disabled" and to drop DoT if
  Firefox-ESR offers no extension API to control it; **or**
- (b) extend FR-004, research §10, T034b, and T055 to (i) verify DoT is off via
  the appropriate Firefox preference (likely `network.trr.mode` and friends; if
  the WebExtensions API can't reach those, that is itself a constitution problem
  to resolve), and (ii) require WebRTC fully disabled rather than
  `disable_non_proxied_udp`.

Until one of these lands, this is a **constitution MUST violation** and blocks
`/speckit-implement` per the skill's operating constraint
("Constitution conflicts are automatically CRITICAL").

**F3 — Inter-plane mutual ed25519 auth: framing not pinned.**
"Mutual ed25519 authentication on each socket" is asserted in
`contracts/control-grpc.md` §"Transport invariants" and in T016/T038/T045, but
the **framing is not specified**. gRPC's stock auth is mTLS over X.509;
ed25519 isn't standard CA-issued. Possible framings: (a) X.509 self-signed
ed25519 leaf certs verified via a local trust store, (b) custom
`Server/ClientCredentials` doing a Noise-style handshake over UDS, (c)
application-layer mutual auth after the gRPC connection. Each has different
test surfaces.

*Fix*: Add a paragraph to `contracts/control-grpc.md` §"Transport invariants"
pinning the framing (likely (a) — X.509-wrapped ed25519, with `cp.pub` / `dp.pub`
as the trust anchors). Without this, T038 and T045 will diverge from T022's
contract-test surface and the implementer will rediscover the question
mid-implementation.

**I12 — FR-018 says "AUTH_REQUIRED on all requests" — wrong for SOCKS5 path.**

*Fix*: Reword to "the proxy rejects every inbound request as unauthenticated —
`0x01 0xFF` on the SOCKS5 path, HTTP 407 + AUTH_REQUIRED on the CONNECT path

**I15 — Outbound SOCKS5 auth shape (DP → tor:9050) underspecified.**
T047: "pass SOCKS5 `UNAME` through verbatim as the upstream SOCKS5 username".
The **password** field on the DP→Tor outbound SOCKS5 dial is not pinned.
Tor's `IsolateSOCKSAuth` keys on (username, password); if the password is
set to the inbound bearer token, that's a secret-leak path (Tor logs even
with `SafeLogging 1`); if it varies for any other reason, isolation could
fracture unexpectedly.

*Fix*: Pin in T047: "DP→Tor outbound SOCKS5 dial sends the per-request
first-party as `UNAME` and an **empty password** (or no auth method at all —
depending on what `golang.org/x/net/proxy.SOCKS5` supports cleanly). The
inbound bearer token is **never** forwarded as outbound auth."
Add a contract-test assertion (extend T032 or a new test in `tests/contract/tor/`)
capturing the outbound SOCKS5 bytes and verifying the password field is empty
/ unset.

**I16 — Cookie-file readability for T062 not pinned.**

created by the in-container `tor` user (group = Tor's primary group inside the
container). The test harness runs from outside the container; for
group-readable to help, the CI user must be in the same numeric GID. No task
pins the `tor` user's GID inside the container, nor how it maps to the host
filesystem.

*Fix*: Either (a) declare a fixed GID for the `tor` user in
`sidecars/tor/Dockerfile` (T014) and either have T062 run as that GID or via
`docker exec` from inside the container, or (b) document the access path
explicitly in `contracts/torrc.md` (paired with I17).

and pushes a generation, the DP accepts the matching token.
