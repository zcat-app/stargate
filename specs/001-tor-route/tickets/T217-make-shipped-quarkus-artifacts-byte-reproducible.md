# T217: Make shipped Quarkus artifacts byte-reproducible

## Context

T109's Ubuntu OpenJDK 25 versus Azul Zulu 25/Debian 13 comparison found byte differences in the shipped Quarkus `generated-bytecode.jar`, `transformed-bytecode.jar`, and `quarkus-application.dat`. Source inspection identified Hibernate/Byte Buddy proxy suffixes, Quarkus recorder/config generation order, absolute-path-dependent transformed-input sorting, and downstream serialized-index order; the captured output also varied in gRPC interceptor order and Arc-generated inactive-bean message fragments. The generated Arc bean constructor descriptor matched across builds; constructor-parameter order was not the differing property. Quarkus 3.40.1 source contains fixes for the generated-name, recorder/config, gRPC, and Arc message-order differences; it retains absolute-path input sorting. T217 will promote the current 3.40 LTS only alongside an enforced source/Maven-cache relative layout and reviewed architecture reconciliation. T109's cross-host gate remains incomplete until exact shipped-byte equality passes.

## Analysis

- **Must hold:** every shipped JVM fast-jar output is byte-identical for the accepted build contract, with no output masking or undocumented variance; any enforced source/cache layout is actually used by the release workflow; build fixes preserve classpath precedence, proxy behavior, interceptor order, Arc injection, and archive/index associations.
- **Gated:** focused producer fixtures, behavior tests for changed generators/orderings, and T109's existing exact-byte comparison.
- **Residue:** other host/toolchain combinations beyond the accepted JDK vendor/libc/non-root dimensions are not claimed; any remaining path assumptions must be explicit in the build contract and release invocation.
