## Clarifications

### Session 2026-05-17

- Q: Tor sidecar image — which upstream do we pin? → A: Stargate-built
  image from `deb.torproject.org` (Tor Project's official Debian apt
  repository), layered on a pinned Debian-slim base, sha256-pinned in
  the compose file. Rationale: shortest provenance chain for the
  in-TCB Tor binary; security updates flow through the Tor Project's
  own pipeline rather than a community fork's release cadence.
- Q: When does the control plane re-read `tokens.yaml` after the user
  edits it? → A: Startup-only. Token add/revoke requires restarting
  the control-plane container; the data plane keeps serving with its
  last-known token list during the restart (Principle II). Live-reload
  plumbing is deferred to the dashboard-UI feature.
- Q: Bearer-token format for the v1 manual flow? → A: 128-bit hex
  (32 characters), generated by the user with `openssl rand -hex 16`.
  Rationale: loopback-only proxy port; 128 bits of entropy is
  appropriate; 32 chars is paste-friendly without sacrificing the
  practical security margin (an attacker reaching the loopback port
  has local code execution per THREAT-MODEL §3.1, already game-over).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - First-time onion service load (Priority: P1)

A privacy-conscious user, freshly installed, can visit a `.onion` URL in
Mullvad Browser and have the page load through Tor, with no DNS leak and
no observable clearnet metadata about the destination.

**Why this priority**: This is the **MVP**. Without this scenario passing,
the project has no demonstrable value — no privacy property is delivered.
It exercises the full vertical: extension → port 8881 → data plane → Tor
sidecar → Tor network → onion service. If this story works, the rest of
v1 is filling in routes; if it does not, nothing else matters.

**Independent Test**: A fresh Mullvad Browser profile with the Stargate
extension installed and a bearer token pasted into the extension settings
loads `https://duckduckgogg42xjoc72x3sjasowoarfbgcmvfimaftt6twagswzczad.onion/`
(DuckDuckGo's v3 onion address, used as a stable reference target) and
renders the page. Release-cadence component observations capture Tor in its
network namespace, CP in its `network_mode: none` namespace, and DP OUTPUT
attempts under T162's host-network/UID-5102 boundary. They check Tor SYNs
against Tor's accepted microdescriptor consensus, CP's loopback-only packet
surface, and the absence of prohibited DP attempts. DP NFLOG records are
observed before the T162 verdict and do not prove a packet reached a physical
NIC or hypervisor; those claims require capture at that vantage. The separate
T034 DNS gate observes UDP/53 in its test namespace and does not establish
browser-wide DNS absence.

**Acceptance Scenarios**:

1. **Given** a freshly installed Stargate local-profile stack
   (`docker-compose.local.yml` up, authenticated Tor observer READY, bearer token
   present in the extension), **When** the user opens a known `.onion`
   URL in Mullvad Browser, **Then** the page renders, the extension's
   per-tab indicator shows the main-navigation decision = Tor (scope below), and the SOCKS tunnel carries page bytes without a
   Stargate failure reply.
2. **Given** the same stack, **When** the user opens
   `http://check.torproject.org` via the onion mirror (or, equivalently,
   any `.onion` whose page asserts Tor-routedness), **Then** the page
   confirms Tor usage. (Equivalently, an integration test asserts the
   destination saw a Tor exit / onion endpoint, not the host's clearnet
   IP.)
3. **Given** the release-cadence T034f component observers during a routed
   onion transfer, **When** the capture and OUTPUT-attempt records are
   analysed, **Then** Tor TCP SYNs match IPv4 OR endpoints parsed from the same
   cookie-authenticated ControlPort response that supplies validity metadata;
   a repeat authenticated query after measurement has the same digest. CP emits
   no observed non-loopback packet, and DP makes no
   prohibited attributed IP attempt. Before real init, refuse any existing or
   unreadable UID-5102 process/socket inventory and validate the complete
   prepared-artifact closure plus independently expected pinned helper/tool
   identities before real init. Do not discover or build in this artifact-only
   native window; ordinary source-init retains its separate initializer/Buildx
   discovery. Tor capture and authenticated
   consensus metadata begin before routed controls and remain active through
   post-workload controls and output quiescence. Positive attribution uses
   distinct exact IPv4 reply controls before and after the >=120-second workload;
   IPv4/IPv6 inverse-cgroup SYN controls appear exactly once in their respective
   groups and reconcile with exact DROP deltas. IPv6 positive attribution is
   not claimed as live calibrated. CP runtime mode is `none`; inventory every
   interface and capture all of them (or prove `lo` is the only interface),
   with exact loopback controls before and after the workload.

   One continuous pair of NFLOG readers spans calibration, workload,
   post-workload controls, and final DP shutdown. Freeze and terminate only the
   verified UID-5102 DP cgroup after the post-control. Keep readers active until
   all observed/inventoried DP TCP tuples, including TIME-WAIT rows with zero
   UID/inode, disappear from the host tables and UDP sockets are closed; then
   require CONFIG UNBIND ACK, same-socket nonblocking EAGAIN drain, sequence
   continuity, zero ENOBUFS/MSG_TRUNC, exact post-drain record/counter equality,
   and exact T162 DROP deltas. The helper verifies the independently expected
   test-binary SHA-256 before socket open and requires kernel
   `6.8.0-146-generic`, recording both. A frozen candidate manifest binds init,
   Compose, build inputs, tools and running image identities; sanitized receipt
   binds the same-run observation and exact cleanup/restoration evidence. CP
   capture cannot detect a failed connect that emitted no packet. This
   observation does not assert what a physical NIC or hypervisor saw; that
   requires measurement at that vantage.

T218 readiness is a prerequisite, not T034f acceptance. The
[qualification boundary contract](contracts/qualification-boundary.md) defines source/platform/live
stages, artifact-only runtime, single-use candidates, shared exclusion, deadlines and completion.
Pre-init UID/socket and artifact checks precede init; production-DP identity and enforcing-label
checks follow init. A SOCKS negotiation control is not routed application evidence. Existing source
is not certified compliant, and original FAIL/NOT OBSERVED scenario records remain unchanged.

### Per-tab indicator scope — T150

The indicator describes the latest observed top-level navigation request's routing decision
(`type: main_frame`, `frameId: 0`) for the active tab, including redirect targets. It is not
a whole-tab protection indicator or proof of successful tunnel establishment. Subresources,
subframes and workers cannot replace this decision. A Direct main request with an onion image
therefore remains Direct (unrouted); an onion main request with a Direct image remains Tor.
Both display: `Other requests may use different routes. Connection success is not verified.`

Canonical prefixes are `Main navigation decision: Tor`,
`Main navigation decision: Direct (unrouted)`, `Main navigation decision: Blocked by Stargate`
and `Main navigation decision: Unknown`. Only a recorded Tor decision permits the Tor label;
only an intentional Direct decision permits the Direct label. A protected main request canceled
by Stargate permits the Blocked label. Unknown tabs, pending decisions, missing or malformed
replies and unreadable background state display Unknown without throwing or deriving a route from
the URL. The Blocked label reports the router's cancellation result; a notification is only UX
and is never credited with canceling traffic.
New main requests replace the old decision immediately with pending state; delayed completions
cannot overwrite a newer decision or repopulate a closed tab. Popup refreshes similarly discard
older replies. State stays in background memory and is removed on tab close or background restart.
This scope supersedes the unqualified labels in historical T034c/T057 task text and walkthroughs.
It changes no route descriptors, hardening gates or T157 failure-enforcement obligations.

Two protection preconditions are stated before any route (T188). Where the extension runs without
private-window access (not confirmed or unreadable counts as missing), the popup shows only:
`Stargate is not protecting private windows: "Run in Private Windows" is not allowed or not
confirmed. Stargate blocks the .onion requests it can see. Allow it in about:addons > Stargate.`
Independently, when the live browser proxy settings differ from the shipped profile baseline or
cannot be read, the label is prefixed with `Warning: the Stargate fail-closed proxy baseline of this
profile is missing, changed or unverifiable, so requests Stargate does not route follow the browser
proxy settings. Reinstall browser-profile/user.js (quickstart).` Each state also raises one
notification stating that protected routing is blocked or unverified; Firefox rejects
`requireInteraction`, so the notification is transient and the popup is the persistent report. In permanent private browsing an extension without private-window access
never starts, so neither message can appear there; the profile baseline below is what fails
closed in that case.

### User Story 2 - Stream isolation per first-party domain (Priority: P2)

When the user opens two different `.onion` services in two different
tabs, distinct full device/profile/initiating-site partitions must not share a Tor circuit. This
prevents cross-partition circuit sharing; it does not promise protection against every correlation
channel or require requests within one partition to use exactly one circuit.

**Why this priority**: This is the privacy property Principle III pins as
load-bearing for Tor: per-first-party stream isolation. The MVP (US1)
proves the path works; this story proves the **privacy claim**. Without
it, two onion sites visited from the same browser share a circuit and the
privacy property the spec advertises does not hold.

**Independent Test**: Exercise the same reachable target through the data plane using distinct
full partitions, so destination-specific rendezvous circuits cannot hide fused credentials. Bind
successful streams to nonzero BUILT circuits through authenticated Tor control observations.
Separately verify browser partition derivation and missing-context blocking under FR-002. A
sidecar-only corpus count does not prove browser/data-plane coverage.

**Acceptance Scenarios**:

1. Distinct full device/profile/initiating-site partitions to the same reachable target through
   port 8881 MUST attach to disjoint circuit IDs. Vary each partition axis using the foundation
   contract's identities, not bare destination strings as production usernames.
2. The test MUST include a controlled credential-fusion discriminator. Its observations must
   distinguish the correct forwarding path from a path collapsing distinct partitions; invalid
   setup or inability to observe that distinction is not PASS or behavioral RED.
3. Same-partition circuit reuse is permitted, not guaranteed. A pinned-version same-credential
   sharing control may calibrate the discriminator; failure to observe that control makes that
   run inconclusive, not proof of a product violation of a same-circuit guarantee.
4. Preserve the existing 100-identity/95-circuit statistic as ancillary sidecar evidence only.
   It cannot tolerate or excuse any observed cross-partition sharing in the required gate.

### User Story 3 - Privacy-safe failure when Tor is down (Priority: P3)

When the Tor sidecar is unreachable or refuses a destination, an authenticated
SOCKS5 request receives only the fixed RFC 1928 failure reply. It contains no
destination, sidecar reason or application bytes. HTTP CONNECT is unsupported on
Tor port 8881 and closes silently on first byte `C`, independently of Tor state.

**Independent Test**: Stop Tor; issue an authenticated SOCKS5 CONNECT through
port 8881. Assert the exact ten-byte `05 03 00 01 00 00 00 00 00 00` reply
and EOF, with no leak-corpus match or extra bytes. A live-sidecar refusal and
a bounded timeout similarly use REP `0x04` and `0x06`. Test the future HTTP
error renderer separately; it is not reachable from this Tor ingress.

**Acceptance Scenarios**:

1. With Tor stopped, authenticated SOCKS5 CONNECT returns the fixed `ROUTE_DOWN`
   reply above and closes. An advisory `SidecarEvent` alone does not cause it.
2. With Tor accepting but refusing a target, the reply is exactly
   `05 04 00 01 00 00 00 00 00 00`; a deadline returns
   `05 06 00 01 00 00 00 00 00 00`. Neither includes upstream text.
3. The full reply bytes and diagnostics contain zero leak-corpus matches;
   an HTTP `C` request receives zero bytes and causes no upstream dial.

### Edge Cases

These are the conditions the spec must keep working privacy-safely
through. Each one drives at least one test in the privacy-critical
tests-first suite (Principle VII).

- **WebSocket upgrade through the SOCKS CONNECT command**. The extension routes a
  `wss://*.onion` request; the data plane tunnels the CONNECT to the Tor
  SOCKS5 sidecar without parsing the upgrade traffic. After the SOCKS5
  handshake completes, the data plane is a byte pipe (Principle I — no
  payload parsing). WebSocket frames pass through unmodified, and the
  connection survives long-lived bidirectional traffic.
- **HTTP/2 connections (forced fallback from QUIC)**. The hardening audit
  has already disabled QUIC/HTTP3 at the browser (Principle III /
  THREAT-MODEL §5.5). Connections fall back to HTTP/2 over TLS over the
  Tor circuit. The data plane sees only SOCKS negotiation; the TLS/H2
  payload is opaque.
- **Concurrent requests against the same first-party domain**. Multiple
  parallel CONNECTs for resources under the same first-party `.onion`
  may reuse a circuit with the same full partition identity. Tor may also choose a new
  circuit; US2 scenario 3 is a calibration condition, not a same-circuit product guarantee.
- **Tor circuit failure mid-request**. The upstream Tor circuit drops
  while bytes are in flight. The data plane MUST NOT retry the request
  itself (Principle I — it is not aware of HTTP semantics on the wire
  after CONNECT). The TCP connection to the browser closes; the browser
  surfaces a normal connection error. **No upstream-derived information
  is propagated** to the browser through error headers or response
  bodies (the data plane has none at that layer to leak).
- **Bearer token missing or invalid**. On SOCKS5, reject with the two-byte
  RFC 1929 `0x01 0xFF` reply and close. HTTP `C` is refused before auth,
  regardless of credential appearance; it gets zero response bytes and
  no counter increment. No token, verifier, destination or username enters
  diagnostics (Principle III).
- **Hostname is `.onion` but unreachable**. After authenticated SOCKS5
  admission, translate the sidecar's refusal to the fixed 10-byte REP `0x04`
  response; never forward SOCKS reason text, destination or application bytes.
- **Extension disabled mid-session**. The user disables or uninstalls
  the Stargate extension while a session is in progress. New browser
  requests no longer go through the proxy; existing connections on port
  8881 continue to be served. The data plane has no extension presence
  signal and does not need one — it serves the port until the OS or the
  browser closes the socket. The privacy effect is the user's
  responsibility: from the moment the extension stops routing, the
  browser's own network stack reaches destinations directly, with no
  Stargate involvement. (This is documented in the install-time
  hardening audit; THREAT-MODEL §3.1 already covers "other software /
  configurations on the same host bypass Stargate".)

## Requirements *(mandatory)*

### Functional Requirements

Numbered for traceability. Each is testable against the privacy-critical
tests-first suite (Principle VII) before implementation lands.

#### Extension behaviour

- **FR-001**: The browser extension MUST route any request whose
  requested destination hostname ends in `.onion` to the proxy at `127.0.0.1:8881` via
  SOCKS5. Other hostnames are out of scope for this feature; the
  extension MAY fall back to direct browser behaviour or to "ask user"
  for non-`.onion` hosts (UI surface for that is deferred to a later
  feature spec). For non-`.onion` requests in this feature, the
  extension simply does not invoke port 8881.
- **FR-002**: Every protected request with trustworthy context MUST carry the isolation identity
  defined by `contracts/foundation-boundaries.md` §“Browser SOCKS isolation identity — T136”. The
  partition contains authenticated device, browser profile and initiating top-level site, plus its
  normal/private and contextual-identity mode. DNS sites use Firefox 153's native
  ICANN-and-PRIVATE `publicSuffix.getDomain()` result with unknown/plain suffixes refused, never a
  last-two-label guess; complete onion identities and canonical IP literals remain distinct.
  Nested contexts bind through `documentId`/`parentDocumentId`, not a tab-only cache.
  Missing/untrustworthy top-level context has no destination fallback
  and MUST produce no routable identity. T157 owns browser cancellation for that result.
  The SOCKS5 username is the exact 68-byte `sg1:` HMAC representation from the boundary contract;
  the password is the device bearer token. The data plane forwards the username unchanged and an
  empty upstream password, so Tor never receives the bearer. Privacy-critical tests MUST prove
  distinct usernames for the same destination under distinct site/device/profile partitions;
  T126/T155 separately prove the same-target circuit outcome in the running stack.
- **FR-003**: The extension MUST set `proxyDNS: true` (Firefox
  WebExtensions `proxy.ProxyInfo`) in the descriptor it returns from
  `proxy.onRequest` so that DNS resolution is delegated to the
  upstream SOCKS5 endpoint (SOCKS5h). SC-003/T034a owns the complete real-browser DNS
  measurement at its recorded loopback and egress capture points, with separate encrypted-DNS
  hardening evidence. T034 is the narrower per-PR UDP/53 measurement in its test network namespace;
  it does not establish browser-wide, TCP DNS, DoH or DoT absence. US1 scenario 3/T034f is the
  separate component-egress/DP OUTPUT observation, not the DNS measurement.
- **FR-004**: Non-Direct routing is fail-closed against a hardened
  target-browser profile. (a) The extension ships only in a release whose
  live-e2e hardening test (`tests/live-e2e/mullvad-browser-hardening/`) was
  green against a test profile that models the target browser's hardened
  defaults (DoH off, DoT off, HTTP/3 / QUIC off) — this is a **release-
  process** precondition, not a per-session runtime check. (b) At runtime,
  the extension gates WebRTC via the stable
  `browser.privacy.network.peerConnectionEnabled` API (the only hardening
  surface Firefox's stable WebExtensions API exposes — sol-review B4). If
  WebRTC is enabled at runtime, the extension MUST raise a notification
  naming WebRTC and the remediation (architecture spec §14.5 failure UX; Gecko
  rejects `requireInteraction`, so the notification is transient and the popup's
  blocked state is the route report), MUST keep only finite current volatile hardening status
  and remove the obsolete legacy hardening storage key at startup (T205), and MUST NOT route non-Direct
  requests through port 8881 until the user remediates. The shipped profile
  template (`browser-profile/user.js`) sets `media.peerconnection.enabled=false`,
  because Mullvad Browser's default is enabled. The extension does
  NOT claim to read or write the DoH/DoT/HTTP-3 preferences via the
  WebExtensions API; those three surfaces are release-cadence-verified, not
  runtime-enforced, and their post-verification drift is accepted residue
  (THREAT-MODEL §5.4/§5.5). (Aligns with Constitution Principle III bullet 3
  as amended by T091 — non-Direct routing is fail-closed at runtime against
  WebRTC; DoH/DoT/HTTP-3 are release-cadence-verified.)
- **FR-004a**: For a protected request, failure or unknown state of hardening, credentials,
  isolation context, profile state or asynchronous generation/binding checks MUST cancel the
  request through an asynchronous blocking `webRequest.onBeforeRequest` response. The matching
  `proxy.onRequest` result is never Direct and MUST NOT reject into Firefox's default proxy
  behavior. An allowed Tor result is a SOCKS descriptor followed by a terminal `null` failover
  sentinel, so a refused or unavailable sidecar cannot fall through to browser/system proxy
  settings. The two listeners consume one request-bound decision and revalidate state before
  allowing dispatch. Intentional non-`.onion` Direct behavior remains distinct. T157 verifies the
  descriptor and real-browser network outcomes, including redirects, retries and subresources.
  The Firefox MV2 background page MUST remain persistent so these two listeners cannot disappear
  between protected requests; browser startup is fail-closed until their current request decision
  completes.

#### Data plane behaviour

- **FR-005**: The data plane MUST listen on TCP `127.0.0.1:8881` for
  authenticated SOCKS5 inbound connections from the browser. First byte
  ASCII `C` (HTTP CONNECT) MUST close with zero response bytes, no auth
  evaluation, counter increment or upstream socket; no HTTP success,
  error-template ingress, negotiation extension, retry, fallback or
  configuration bypass is supported. The port-to-upstream binding is fixed
  to Tor at startup (Principle I). T173 implements this T172 contract; its evidence record scopes verification.
- **FR-006**: For supported SOCKS5 requests, the data plane MUST extract
  the bearer from the username/password sub-negotiation (password = token),
  compute `HMAC-SHA-256(pepper, candidate)` once and compare against every
  verifier in the current generation with
  `crypto/subtle.ConstantTimeCompare`, without early exit. Missing or invalid
  credentials receive only `0x01 0xFF` then close. HTTP `C` must not enter
  this auth path. No offered token, verifier, username or rejected target may
  appear in a response, log or counter increment.
- **FR-007**: The data plane MUST forward authenticated inbound bytes
  on port 8881 to the Tor sidecar's SOCKS5 endpoint
  (`unix:///run/stargate-tor/tor-socks.sock` on the DP-only fabric), passing through the
  hostname-mode (SOCKS5h) target address and the SOCKS5 username
  unchanged. The data plane MUST NOT resolve the target hostname
  locally (Principle III). It MUST NOT parse, inspect, or modify
  request or response bytes beyond what SOCKS5 framing requires
  (Principle I).
- **FR-008**: The data plane MUST NOT log the destination hostname,
  the full URL, request or response headers, request or response
  bodies, or any per-request timestamp at finer resolution than the
  ≥1-hour aggregate bucket defined in architecture spec §6.4
  (`aggregate_counters`). Only the per-route, per-hour
  `(request_count, byte_count)` pair is recorded. Only requests that
  pass authentication increment `request_count`; auth failures leave
  the counter unchanged (Principle III — counting them would be a
  side channel for token-guessing attacks; `data-model.md` §3
  records the rule). Route failures (`ROUTE_DOWN`, `ROUTE_REFUSED`,
  `ROUTE_TIMEOUT`) DO increment `request_count` once authentication
  has passed: unlike auth failures they are not attacker-controlled
  in the same way (the attacker cannot induce a route failure at
  will without already routing), and the gap between `request_count`
  and the fraction of buckets with `byte_count > 0` gives the
  operator sidecar-health visibility at negligible privacy cost
  (data-model.md §3 records the asymmetry). **v1 persistence note**:
  in this feature, the aggregates live in data-plane process memory
  only; persistence to the `aggregate_counters` SQLite table via the
  CP→DP `GetStatus` pull (arch §5.2) is deferred to the admin-UI
  feature (data-model.md §3 / `contracts/control-grpc.md`
  §"GetStatus (minimum subset)", which authoritatively records both
  the in-scope test-harness caller and the deferred production
  caller). The invariant on *what* is counted (this FR)
  is independent of the deferral on *where* the counts persist.
- **FR-009**: After authenticated SOCKS5 admission, upstream dial or
  handshake outcomes alone determine route failure. `SidecarEvent` is
  advisory and cannot gate admission (Principle II). Return only the fixed
  ten-byte RFC 1928 reply with zero `BND.ADDR`/`BND.PORT`:
  `ROUTE_DOWN→0x03`, `ROUTE_REFUSED→0x04`, `ROUTE_TIMEOUT→0x06`, then close.
  No destination, token, sidecar reason or upstream text may enter the reply
  or diagnostics. HTTP `C` is refused before auth/dial under FR-005; the
  renderer-only HTML format in `contracts/error-template.md` has no Tor-port
  ingress claim.
- **FR-010**: Local DP route and CP admin/health listeners MUST bind loopback in
  their own namespaces and at host publication. LAN/VPS MUST use the actual tunnel
  interface in each listener namespace and remain closed on tunnel loss. No container
  environment flag, wildcard bind or tunnel elsewhere in the stack is an exception.
  T125's permission is superseded. T134 selected the topology; T162 implements it and
  T168 adds mandatory process confinement before admission, independent of auxiliary
  owner-rule persistence; T163 verifies production namespaces and packet outcomes. See
  `contracts/foundation-boundaries.md` §Deployment and authority.

- **FR-011**: The Tor sidecar MUST be configured with the directive set
  pinned byte-for-byte in `contracts/torrc.md §"Rendered file"`:
  `SocksPort unix:/run/tor-fabric/private/tor-socks.sock IsolateClientAddr IsolateSOCKSAuth`,
  `ControlSocket /var/lib/tor/control/tor-control.sock`, `CookieAuthentication 1`,
  `CookieAuthFileGroupReadable 1`, `DataDirectory /var/lib/tor`,
  `ClientUseIPv6 0`, `AvoidDiskWrites 1`, `UseBridges 0`,
  `Log notice file /dev/null`, `SafeLogging 1` (T152 / Constitution III). For this static Tor-only slice
  the safe `torrc` is **baked into the Tor image at build time**
  (`sidecars/tor/Dockerfile`, T087) and loaded by the entrypoint at
  container start; the control plane does NOT render `torrc` at boot
  (Constitution Principle II — Compose starts Tor before the CP, so a
  CP-rendered `torrc` would couple Tor startup to control-plane
  availability; sol-review B2). `DataDirectory /var/lib/tor` is explicit
  because the entrypoint does not load Debian's `torrc-defaults`, so
  without the directive Tor would fall back to `$HOME/.tor` and land the
  control cookie at the wrong path (T087 / sol-review B2+M3).
  Control-plane-rendered `torrc` (atomic write into the
  `stargate-tor-config` volume) is future work for a dynamic-config
  feature and is deferred by T089 (T037 `TorrcRenderer` is deferred with
  it). Bridge lines MUST be absent from the image-baked `torrc` for this
  feature (bridges are a separate feature spec). **A contract test
  (`tests/contract/torrc/render_byte_match_test.go`, per T029) MUST
  verify the `torrc` template in `contracts/torrc.md` is byte-for-byte
  equal to the pinned Go golden** for v1 of this feature; T087's
  cold-volume regression test verifies the `/etc/tor/torrc` baked into
  the image equals the same golden without harness-seeded config.
- **FR-012**: Tor MUST have no TCP SOCKS or control listener or host port
  publication. Its native SOCKS Unix socket is in a Tor-private directory;
  the image-owned hook hardlinks that inode at mode 0660 into a DP-only
  volume. The DP may dial only that fixed path. The raw cookie-authenticated
  ControlSocket is in Tor's private state and is reachable inside Tor,
  including by its native publisher, and by the test harness via
  `docker compose exec`. Tor's Docker healthcheck is disabled.
  CP holds no Tor cookie, Tor-cookie group, raw control mount or Docker network
  path. T164 introduced the isolated observer's authenticated finite-health
  endpoint on a CP-only fabric. T203 preserves that endpoint and removes the
  observer's raw Tor authority: the observer reads only a finite boot-time-leased
  publication from the Tor-internal publisher on read-only shared tmpfs, under
  `contracts/foundation-boundaries.md`. Historical T165 evidence does not validate
  this replacement boundary; T203 records the current validation evidence.
  CP health remains advisory, with no raw-control fallback (architecture
  spec §4.2). The installer requires a current authenticated cached READY sample
  within one bounded post-Compose window, default 300 seconds (T124).

#### Inter-plane integration

- **FR-013**: The data plane MUST accept a list of bearer-token verifiers
  (HMAC-SHA-256 tags under the install-time pepper; data-model.md §1.5,
  T092) via the gRPC `ReloadTokens` RPC (architecture spec §5.2) and
  apply it atomically. In this feature, the source of the list is a config
  file read by the control plane at startup (no dashboard UI yet; see
  Assumptions). The data plane MUST continue serving port 8881 with
  its last-known token list if the control plane is unreachable
  (Principle II; architecture spec §5.5). Stale proposals are rejected. Recovery MUST
  distinguish current authority from restored stale content; automatically renumbering an
  older backup to `current + 1` is prohibited by T156. T159 specifies the synchronized
  transition and durable acknowledgment contract before code. Admission is never gated on
  a control-plane event (data-model.md §2; sol-review B3): a request
  that authenticates against the last-known list reaches the upstream
  dial regardless of `SidecarEvent` state.
- **FR-014**: The control plane MUST emit a Tor `SidecarEvent` only for a source observation it can substantiate, with a fixed-vocabulary `detail` token and no free text from Tor logs. In this feature's authenticated health channel it emits `STARTED`, `HEALTHY`, and `UNHEALTHY` as specified in `contracts/control-grpc.md`; it does not emit `STOPPED`, `CRASHED`, or `RESTARTED` because health observations cannot establish those lifecycle events. The data plane validates and delivers matching Tor events to an advisory sink. Receipt of an event MUST NOT create a data-plane operational aggregate or sidecar status, gate listening/authentication/dialing/forwarding, or short-circuit the upstream dial. The control plane records its own source-observed `HEALTHY` / `UNHEALTHY` transitions in the corresponding completed-hour operational categories through the sole writer in data-model.md §4. The data plane MUST attempt the fixed Tor fabric dial for every admitted request; its result alone selects `ROUTE_DOWN` / `ROUTE_REFUSED` / `ROUTE_TIMEOUT`. Stale or forged events cannot suppress a dial that would succeed.

#### Bearer token configuration (v1 manual flow)

- **FR-017**: The control plane MUST read bearer tokens from a config
  file at a documented path (`/etc/stargate/tokens.yaml` inside the
  control-plane container; mounted from a named volume the user
  populates manually for v1). The file format MUST be a list of token
  records, each with a label (free-form string, used only in current authentication
  configuration) and the **plaintext token** (the control plane computes the
  verifier `HMAC-SHA-256(pepper, token)` under the 32-byte install-time
  pepper at read time and never persists the plaintext beyond the file
  the user supplies; T092 — Argon2id is retired, see data-model.md §1.5
  and SECURITY-DECISIONS.md). Each plaintext token MUST be a 32-
  character lowercase-hexadecimal string (128 bits of entropy). The
  README quick-start documents `openssl rand -hex 16` as the canonical
  one-liner. Tokens that do not match the expected format MUST be
  rejected at config-load time with a static redacted error and an operational
  aggregate update; neither label nor offending token bytes may enter logs.
- **FR-018**: The control plane reads `tokens.yaml` **once at startup
  only** in v1. On a successful load, it MUST persist the verifiers and
  the bumped generation (from the `token_generation` record,
  data-model.md §1.8), push the verifier list to the data plane via
  `ReloadTokens` (FR-013), and aggregate operational categories under data-model.md §4.
  No labels, per-event timestamps or detail JSON may be journaled. Missing/unreadable/invalid
  input increments only the permitted category as specified and **does NOT call ReloadTokens** —
  the data plane keeps its last-known list and keeps serving port 8881
  (Principle II "continue routing"). Only a successfully-parsed explicit
  empty list (`tokens: []`) is the revoke-all path: that alone pushes an
  empty generation, after which supported SOCKS auth receives `01 FF`
  on all requests. HTTP `C` still closes before auth. A valid empty list and an I/O/parse failure therefore have
  distinct semantics, by design. Token add/revoke requires restarting
  the control-plane container; per architecture spec §11, the data plane
  keeps serving with its last-known token list across this restart.
  Filesystem-watch and SIGHUP-reload paths are explicitly deferred to
  the dashboard-UI feature.
- **FR-019**: The bearer token configured in the extension's
  `storage.local` MUST match one of the tokens in the control plane's
  config file. The extension UX for pasting/storing this token is in
  scope for this feature at a minimum level: an options page with a
  single field for the token, persisted to `storage.local`, with a
  visible warning that `storage.local` is not credential-grade storage
  (the canonical warning text is pinned in `data-model.md` §5.1; the
  rationale for accepting `storage.local` rather than a keyring path
  in v1 is in `research.md` §6 — Firefox ESR exposes no credential-
  grade storage API to extensions). The architecture spec §14.4
  `NEEDS CLARIFICATION` is **resolved-for-v1 by this FR** in
  combination with `research.md` §6; a future feature may revisit the
  decision if WebExtensions on Firefox ESR gain a credential-grade
  storage API.

### Key Entities

- **Bearer token (device token)** — a per-device opaque secret. Used as
  the SOCKS5 password on Tor port 8881. No HTTP `Proxy-Authorization`
  ingress is supported there. Identifies *the device* to the data
  plane, not the user. Never persisted in plaintext outside the v1
  config file the user creates manually; stored as an HMAC-SHA-256
  verifier under the install-time pepper (T092) in the control-plane
  DB and the data plane's in-memory list.
- **Isolation partition / initiating site** — the authenticated-device, browser-profile and
  initiating-top-level-site tuple defined by the foundation boundary contract. Trustworthy
  browser navigation/document metadata selects the site; the destination is never a missing-context
  fallback. The extension sends only a fixed-length HMAC representation as the SOCKS5 username.
  Neither the clear site nor the isolation username is persisted by the data plane. Per-domain
  routing preferences remain a separate `storage.local` concern (out of scope here beyond
  architecture spec §14.4).
- **Tor circuit** — Tor's internal abstraction for an end-to-end path.
  Not directly observable by Stargate; queried only by the contract
  test against the sidecar's control port for verification. In normal
  operation no Stargate component sees circuit IDs.
- **Stargate aggregate counter** — `(route="TOR", hour_bucket,
  request_count, byte_count)` row in `aggregate_counters`
  (architecture spec §6.4). The only persistent record this feature
  creates about Tor traffic.
- **Privacy-safe Tor failure reply** — a fixed SOCKS5 RFC 1928/1929 byte
  sequence with no destination or upstream text. The HTML template in
  architecture §10 is a future renderer format with no Tor-port ingress.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time user with Mullvad Browser installed completes
  the steps "install Stargate extension → paste bearer token → load a
  known `.onion`" in **under 5 minutes** of wall-clock time on a
  clean browser profile in a private local or remote/virtual browser session,
  **without** consulting any documentation
  beyond the project quick-start (`specs/001-tor-route/quickstart.md`
  in this feature; a top-level README will mirror or supersede it in a
  later feature). The first-time human operator starts the timer at extension
  installation and stops it when the page renders; T077 records the complete
  clean-checkout setup duration separately. Agent-driven automation is functional
  evidence only and cannot satisfy this human usability criterion. Measured by
  the T077 walkthrough; the existing VPS is an allowed remote venue.
- **SC-002**: No observed Tor circuit may carry streams from distinct full authenticated-device,
  browser-profile/context and initiating-site partitions. Required same-target evidence through
  the data plane must bind successful streams to nonzero BUILT circuits, vary each partition axis,
  and include a valid credential-fusion discriminator. FR-002/foundation browser derivation and
  real-browser blocking evidence remain separate mandatory layers; direct sidecar tests cannot
  establish them. Same-partition circuit reuse is permitted, not guaranteed. The historic T061
  100 synthetic labels / >=95 distinct identity-tagged circuits remains an ancillary sidecar
  statistic: it does not establish completed CONNECTs, production `sg1:` identities, browser/DP
  forwarding or absence of cross-partition sharing. Historic results and the 2026-09-07 addressing
  decision remain preserved; no leak is inferred solely from this acceptance correction.
- **SC-003**: During a continuous **10-minute Mullvad Browser session
  loading only `.onion` content through repeated, demonstrably successful
  page loads** via a Local-profile Stargate stack, complete simultaneous captures on the
  measured Linux x86_64 guest-host's loopback interface and active egress
  interface contain **zero** DNS queries (A, AAAA, MX, or otherwise) for any name ending
  in `.onion`. Canonical assertion: no DNS packet's query or answer
  fields contain a hostname matching `*.onion`. Wireshark/tshark
  display filter: `dns.qry.name contains ".onion" || dns.resp.name
  contains ".onion"`; expected zero matches across both interfaces.
  T034a may use the existing VPS as the Local-profile host and bounded
  automation through the ordinary browser interface. It records the exact
  browser build and channel, a fresh supported full profile with the reviewed
  extension, successful page-load evidence throughout the interval, complete
  capture start/stop and zero drop/truncation counts, and safe pre/post positive
  controls that show DNS queries and answers are visible on each captured
  interface. Controls must never send a real `.onion` name to a public resolver.
  `tcpdump` capture with grounded, pinned `tshark` offline analysis is permitted.
  A VPS result asserts decoded DNS absence only at its guest-host `lo` and
  active egress capture points; it does not establish physical-NIC, hypervisor,
  other namespace or encrypted-DNS absence. This VPS venue permission applies
  only to SC-003's DNS measurement and does not prove the separately owned US1
  egress-consensus assertion (T034f). An Alpha-browser result covers only
  its recorded Alpha environment and does not establish stable-browser support;

  The per-PR gate (T034) implements the same assertion via `gopacket`'s
  DNS-layer parse; the release-tag measurement (T034a) and the

- **SC-004**: Each authenticated SOCKS5 route failure in this feature

- **SC-005**: The Tor-route data plane handles a sustained

## Assumptions

These are reasonable defaults the spec adopts where the input prompt or
the architecture did not pin a choice. Each is recorded so a later
clarification round (`/speckit-clarify`) can revisit them deliberately.

- **Feature-preview boundary.** This 001 delivery is an internal Local/JVM/Linux-amd64 `feature-preview`, not completed v1 or a public release. Candidate and signed release manifest carry `channel: feature-preview`; prepared GitHub Release metadata must set `prerelease: true`. Native CP, Local/LAN/VPS profiles and runtime-verified supported architectures remain required before completed v1. T081 implementation authorizes no tag creation or publication. A public preview is the first public release and requires Constitution Governance and VIII external-human review.

- **Local profile only for this feature.** LAN and VPS profiles
  (architecture spec §3 profiles) are explicitly out of scope here, per
  the user input. They are revisited in a separate feature spec once
  the local-profile slice is proven. FR-010 follows T156's actual-listener and
  host-publication loopback rule. T134 must replace the withdrawn T125 exception;
  its current topology is not evidence of compliance.
- **No bridges.** Tor bridge support (Constitution v1 Scope) is
  delivered as a separate feature spec. The `torrc` baked into the Tor
  image by this feature has `UseBridges 0` and no `Bridge` lines (FR-011).
- **Manual bearer-token configuration for v1.** The control-plane reads
  tokens from a yaml file the user populates (FR-017). The admin
  dashboard UI, including the enrollment flow with QR/JSON exchange
  (Constitution v1 Scope), is a separate feature; this feature only
  needs *some* bearer-token loading mechanism, and a config file is
  the smallest viable choice.
- **No Quarkus dashboard UI yet.** The control plane runs (it has to —
  it owns the token loader and the gRPC server to the data plane) but
  exposes no HTTP admin UI for this feature. The existing `/healthz` endpoint
  accepts only the effective literal `127.0.0.1` through a pre-listen guard
  (T204); HTTPS, HTTP domain sockets and framework management are unsupported.
  It is not used for Docker health history; Compose healthchecks are disabled
  under Constitution III. The admin UI lands in a later
  feature; this slice deliberately defers it to keep the cone small.
- **Reference target onion service for the success-criterion tests.**
  The integration suite uses DuckDuckGo's v3 onion address
  (`duckduckgogg42xjoc72x3sjasowoarfbgcmvfimaftt6twagswzczad.onion`,
  long-lived and widely-cited; if it becomes unreachable the test
  harness must update the address and record the change in
  `SECURITY-DECISIONS.md`). For US2's circuit-isolation test, the
  harness uses a synthetic corpus of 100 distinct onion-style address
  *strings* presented to the SOCKS5 layer as the per-connection
  isolation key (the SOCKS5 username, FR-007); the sidecar's per-label
  circuit assignment is observed directly through the control port as ancillary evidence only.
  The required full-partition gate is SC-002; the corpus does not model production usernames.
  *(Amended 2026-09-07, T061 escalation → amend-spec: the prior claim
  that "reachability is not required … only that the Tor sidecar
  attempts distinct circuits" toward the corpus strings is false on the
  pinned image — the sidecar neither parses them (invalid Ed25519 keys)
  nor builds any circuit toward an unpublished address; see SC-002's
  amendment note.)*
- **`AUTH_REQUIRED` is a new error code added by this feature.** The
  architecture spec §10.1 enumerates `ROUTE_DISABLED`, `ROUTE_DOWN`,
  `ROUTE_TIMEOUT`, `ROUTE_REFUSED`, `BIND_REFUSED`. `AUTH_REQUIRED`
  (SOCKS5 auth-fail `01 FF`; HTTP 407 is renderer-only future format) is added here for the
  bearer-token-missing/invalid case (Edge Cases & FR-006). The
  architecture spec is amended in lock-step with this feature's first
  implementation PR to record the new code; until that lands, the spec
  carries the addition as a known follow-up.
- **Reproducibility holds for the Go data plane in this feature.** The
  byte-reproducible build tier (Principle VI; architecture spec §12.1)
  applies; the `tests/reproducibility/` harness exercises the data-
  plane build twice and `cmp`s. Native-image reproducibility for the
  control plane is best-effort and is not load-bearing for this
  feature's success criteria.
- **Mullvad Browser / Firefox floor.** The extension uses WebExtensions MV2
  `proxy.onRequest`, native `publicSuffix.getDomain()` and document-bound request metadata as
  documented in architecture spec §14.1. The manifest sets Gecko `strict_min_version` to `153.0`,
  so older Mullvad Browser builds reject the extension rather than running a weaker isolation
  path. Alpha builds are development evidence only: v1 does not release until stable Mullvad
  Browser uses Gecko 153 or newer and retains MV2. If that stable release drops MV2, redesign and
  constitutional review replace this assumption; there is no silent legacy fallback.
- **Browser precondition: private-window access and the fail-closed profile baseline (T188).**
  Mullvad Browser runs every window in private browsing, and a temporarily loaded extension has no
  private-window access until the user allows "Run in Private Windows"; without it the extension
  never starts in permanent private mode. Any request the extension does not route with a Tor
  descriptor, including its `{type:'direct'}` result, follows the browser's own proxy settings.
  The dedicated Stargate profile therefore ships `browser-profile/user.js`: manual SOCKS5 with
  proxy-side DNS to the T186 Unix sink, bypassed (`no_proxies_on`) only for `<local>` and the
  ICANN top-level domains from the recorded `publicsuffix` package (`onion` and `arpa` excluded).
  With the extension absent or not running, `.onion` in every form and any unknown TLD fail
  closed while ICANN clearnet connects directly, as the extension's non-`.onion` route does. This
  baseline is scoped to 001, where only `.onion` is protected; a feature that protects clearnet
  must revisit the allowlist. Residues, disclosed in the quickstart: skipping the baseline
  reverts to the browser's configured proxy settings; a TLD delegated after the recorded list,
  a trailing-dot clearnet name (`example.com.`) and non-loopback IP literals fail closed in this
  profile, with or without the extension, because its Direct result falls to the baseline (a new
  TLD needs a reviewed list update; CIDR entries do not bypass IP literals); an emptied or garbled
  `network.proxy.socks` falls open for non-bypassed names, which the running extension's
  `proxy.settings` comparison reports. The extension blocks protected routing while its own
  private-window access is missing or unconfirmed.
- **`proxy.onRequest` failover timeout: Firefox default, with no route fallback.** The router
  does not set `failoverTimeout` on the returned SOCKS `proxy.ProxyInfo`
  descriptor; Firefox's default applies before the terminal `null` ends the extension-provided
  chain. The timeout can fail the protected request but cannot select Direct or the browser's
  configured proxy. Pinning the value
  would create a magic number with no spec-level rationale. If a
  future feature needs a tighter or looser failover (e.g. for
  high-latency bridge transports), the change ships with a
  justification in that feature's research doc and an amendment to
  this assumption. See tasks.md T054 for the v1 decision.
