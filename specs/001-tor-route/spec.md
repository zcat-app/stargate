## Clarifications

### Session 2026-05-17

- Q: Tor sidecar image — which upstream do we pin? → A: Stargate-built
  image from `deb.torproject.org` (Tor Project's official Debian apt
  repository), layered on a pinned Debian-slim base, sha256-pinned in
  the compose file. Rationale: shortest provenance chain for the
  in-TCB Tor binary; security updates flow through the Tor Project's
  own pipeline rather than a community fork's release cadence.
- Q: When does the control plane re-read `tokens.yaml` after the user
  edits it? → A: Startup-only. Token add/revoke requires restarting
  the control-plane container; the data plane keeps serving with its
  last-known token list during the restart (Principle II). Live-reload
  plumbing is deferred to the dashboard-UI feature.
- Q: Bearer-token format for the v1 manual flow? → A: 128-bit hex
  (32 characters), generated by the user with `openssl rand -hex 16`.
  Rationale: loopback-only proxy port; 128 bits of entropy is
  appropriate; 32 chars is paste-friendly without sacrificing the
  practical security margin (an attacker reaching the loopback port
  has local code execution per THREAT-MODEL §3.1, already game-over).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - First-time onion service load (Priority: P1)

A privacy-conscious user, freshly installed, can visit a `.onion` URL in
Mullvad Browser and have the page load through Tor, with no DNS leak and
no observable clearnet metadata about the destination.

**Why this priority**: This is the **MVP**. Without this scenario passing,
the project has no demonstrable value — no privacy property is delivered.
It exercises the full vertical: extension → port 8881 → data plane → Tor
sidecar → Tor network → onion service. If this story works, the rest of
v1 is filling in routes; if it does not, nothing else matters.

**Independent Test**: A fresh Mullvad Browser profile with the Stargate
extension installed and a bearer token pasted into the extension settings
loads `https://duckduckgogg42xjoc72x3sjasowoarfbgcmvfimaftt6twagswzczad.onion/`
(DuckDuckGo's v3 onion address, used as a stable reference target) and
renders the page. A simultaneous `tcpdump` / Wireshark capture on the
`lo` interface and on the host's egress NIC confirms:

- No A or AAAA DNS query for any string ending in `.onion` is sent on
  either interface during the session (Principle III — SOCKS5h).
- Egress traffic from the host goes only to Tor guards (matched against
  the current public Tor consensus); no direct connection to any IP not
  in the consensus appears during this load.

**Acceptance Scenarios**:

1. **Given** a freshly installed Stargate local-profile stack
   (`docker-compose.local.yml` up, Tor sidecar HEALTHY, bearer token
   present in the extension), **When** the user opens a known `.onion`
   URL in Mullvad Browser, **Then** the page renders, the extension's
   per-tab indicator shows route = Tor, and the response carries no
   Stargate error template.
2. **Given** the same stack, **When** the user opens
   `http://check.torproject.org` via the onion mirror (or, equivalently,
   any `.onion` whose page asserts Tor-routedness), **Then** the page
   confirms Tor usage. (Equivalently, an integration test asserts the
   destination saw a Tor exit / onion endpoint, not the host's clearnet
   IP.)
3. **Given** a Wireshark capture on `lo` and the host egress NIC for the
   duration of the session, **When** the capture is analysed offline,
   **Then** no plaintext DNS query for any `*.onion` name appears in
   either capture, and no TCP connect to a destination outside the
   current Tor consensus appears on the egress NIC during the routed
   request window.

### User Story 2 - Stream isolation per first-party domain (Priority: P2)

When the user opens two different `.onion` services in two different
tabs, each first-party origin gets its own Tor circuit. Visiting site A
in one tab and site B in another does not let either site's exit-side
observer correlate the user's visits across both.

**Why this priority**: This is the privacy property Principle III pins as
load-bearing for Tor: per-first-party stream isolation. The MVP (US1)
proves the path works; this story proves the **privacy claim**. Without
it, two onion sites visited from the same browser share a circuit and the
privacy property the spec advertises does not hold.

**Independent Test**: With the local-profile stack running, simultaneously
open two distinct `.onion` URLs in two tabs. Query the Tor sidecar's
control port (cookie-authenticated, internal to the compose network) for
the active circuit list, or inspect the sidecar's NEWNYM / STREAM event
log. Assert that the two requests' SOCKS5 streams attached to **distinct
circuit IDs**. Repeated with 10 distinct first-party `.onion` domains in
sequence, assert ≥9 distinct circuits across the 10 visits (one allowance
for legitimate circuit reuse within a short window for the same origin).

**Acceptance Scenarios**:

1. **Given** the local stack with the Tor sidecar's control port
   reachable from the integration-test harness, **When** the harness
   issues two CONNECT requests to two different `.onion` destinations
   through port 8881 in parallel, with SOCKS5 username set to each
   request's first-party domain (the extension does this; the test
   simulates the extension), **Then** the Tor sidecar's `GETINFO
   circuit-status` (or equivalent control-port query) reports two
   different circuit IDs for the two streams.
2. **Given** the same stack, **When** the harness issues 10 sequential
   CONNECTs to 10 distinct first-party `.onion` domains over the course
   of a short window (≤2 min), **Then** at least 9 distinct circuit IDs
   appear across the 10 streams.
3. **Given** the same stack, **When** the harness issues two CONNECTs to
   the **same** first-party `.onion` domain (different resources on the
   same origin) in parallel, **Then** the same circuit ID is used for
   both — same-origin requests intentionally share a circuit (this is
   the design, not a leak).

### User Story 3 - Privacy-safe failure when Tor is down (Priority: P3)

When the Tor sidecar is unreachable or unhealthy, requesting a `.onion`
URL returns the privacy-safe error template defined by the architecture
spec. The error response reveals nothing about destinations, upstream
addresses, sidecar internals, or backtraces.

**Why this priority**: Failure-mode privacy is part of the privacy
property — an error response that leaks destination metadata is a leak
just as much as a successful request that leaks. This is P3 (not P1)
because it exercises the error path, not the happy path; an MVP can
demonstrate value without it, but a release cannot ship without it.

**Independent Test**: Stop the Tor sidecar container
(`docker compose stop tor`). Issue a request to a `.onion` URL through
port 8881. Capture the full response (status, headers, body). Assert
the response byte-for-byte matches the privacy-safe template from the
architecture spec §10.2 after substitution of only the three permitted
fields (`{ROUTE_LABEL}`, `{CODE}`, `{LOCAL_REFERENCE_ID}`). Run the response through the curated leak-corpus
check from architecture spec §10.3 to confirm no forbidden substring
appears in any header or body byte.

**Acceptance Scenarios**:

1. **Given** the local-profile stack with the Tor sidecar stopped,
   **When** a CONNECT to a `.onion` destination is sent through port
   8881, **Then** the data plane responds with HTTP 502 and the body
   matches the architecture spec §10.2 template with `{CODE} = ROUTE_DOWN`
   and `{ROUTE_LABEL} = "Tor"`.
2. **Given** the same scenario, **When** the response headers are
   inspected, **Then** they contain exactly `Content-Type`,
   `Content-Length`, `Cache-Control: no-store`, and `X-Stargate-Error:
   ROUTE_DOWN` — and no other headers (no `Server`, no `Via`, no
   `X-Forwarded-*`, no sidecar version strings).
3. **Given** the contract-test leak corpus (test IPs, test hostnames,
   test circuit IDs, sidecar log fragments), **When** the response body
   and headers are scanned, **Then** no substring from the corpus
   appears.

### Edge Cases

These are the conditions the spec must keep working privacy-safely
through. Each one drives at least one test in the privacy-critical
tests-first suite (Principle VII).

- **WebSocket upgrade through CONNECT**. The extension routes a
  `wss://*.onion` request; the data plane tunnels the CONNECT to the Tor
  SOCKS5 sidecar without parsing the upgrade traffic. After the SOCKS5
  handshake completes, the data plane is a byte pipe (Principle I — no
  payload parsing). WebSocket frames pass through unmodified, and the
  connection survives long-lived bidirectional traffic.
- **HTTP/2 connections (forced fallback from QUIC)**. The hardening audit
  has already disabled QUIC/HTTP3 at the browser (Principle III /
  THREAT-MODEL §5.5). Connections fall back to HTTP/2 over TLS over the
  Tor circuit. The data plane sees only the CONNECT framing; the TLS/H2
  payload is opaque.
- **Concurrent requests against the same first-party domain**. Multiple
  parallel CONNECTs for resources under the same first-party `.onion`
  share one circuit (same SOCKS5 username → `IsolateSOCKSAuth`
  consolidates). Verified by US2 acceptance scenario 3.
- **Tor circuit failure mid-request**. The upstream Tor circuit drops
  while bytes are in flight. The data plane MUST NOT retry the request
  itself (Principle I — it is not aware of HTTP semantics on the wire
  after CONNECT). The TCP connection to the browser closes; the browser
  surfaces a normal connection error. **No upstream-derived information
  is propagated** to the browser through error headers or response
  bodies (the data plane has none at that layer to leak).
- **Bearer token missing or invalid**. On the HTTP CONNECT path, the
  data plane rejects the request with HTTP 407 (Proxy Authentication
  Required) and a privacy-safe body (per architecture spec §10
  template, with `{CODE} = AUTH_REQUIRED` — this is a new error code
  added by this feature; see FR-006). On the SOCKS5 path, the
  rejection is the 2-byte RFC 1929 sub-negotiation failure
  `0x01 0xFF` followed by socket close — no body is sent
  (`contracts/socks5-auth.md` §"Auth failure response"). The CONNECT
  body MUST NOT distinguish "missing token" from "invalid token"
  beyond the fact of auth failure. The data plane MUST NOT log the
  token, the offered token's hash, or the destination of the rejected
  request (Principle III — no per-request metadata).
- **Hostname is `.onion` but the service is unreachable or does not
  exist**. The Tor sidecar's SOCKS5 handshake responds with a SOCKS5
  failure (e.g., `general SOCKS server failure`, `host unreachable`).
  The data plane translates this to the architecture spec §10 template
  with `{CODE} = ROUTE_REFUSED` (the sidecar accepted but refused the
  target) and 502 status. **The data plane MUST NOT include the
  destination hostname or the underlying SOCKS5 reason text** in the
  response body or headers.
- **Extension disabled mid-session**. The user disables or uninstalls
  the Stargate extension while a session is in progress. New browser
  requests no longer go through the proxy; existing connections on port
  8881 continue to be served. The data plane has no extension presence
  signal and does not need one — it serves the port until the OS or the
  browser closes the socket. The privacy effect is the user's
  responsibility: from the moment the extension stops routing, the
  browser's own network stack reaches destinations directly, with no
  Stargate involvement. (This is documented in the install-time
  hardening audit; THREAT-MODEL §3.1 already covers "other software /
  configurations on the same host bypass Stargate".)

## Requirements *(mandatory)*

### Functional Requirements

Numbered for traceability. Each is testable against the privacy-critical
tests-first suite (Principle VII) before implementation lands.

#### Extension behaviour

- **FR-001**: The browser extension MUST route any request whose
  requested destination hostname ends in `.onion` to the proxy at `127.0.0.1:8881` via
  SOCKS5. Other hostnames are out of scope for this feature; the
  extension MAY fall back to direct browser behaviour or to "ask user"
  for non-`.onion` hosts (UI surface for that is deferred to a later
  feature spec). For non-`.onion` requests in this feature, the
  extension simply does not invoke port 8881.
- **FR-002**: Every protected request with trustworthy context MUST carry the isolation identity
  defined by `contracts/foundation-boundaries.md` §“Browser SOCKS isolation identity — T136”. The
  partition contains authenticated device, browser profile and initiating top-level site, plus its
  normal/private and contextual-identity mode. DNS sites use Firefox 153's native
  ICANN-and-PRIVATE `publicSuffix.getDomain()` result with unknown/plain suffixes refused, never a
  last-two-label guess; complete onion identities and canonical IP literals remain distinct.
  Nested contexts bind through `documentId`/`parentDocumentId`, not a tab-only cache.
  Missing/untrustworthy top-level context has no destination fallback
  and MUST produce no routable identity. T157 owns browser cancellation for that result.
  The SOCKS5 username is the exact 68-byte `sg1:` HMAC representation from the boundary contract;
  the password is the device bearer token. The data plane forwards the username unchanged and an
  empty upstream password, so Tor never receives the bearer. Privacy-critical tests MUST prove
  distinct usernames for the same destination under distinct site/device/profile partitions;
  T126/T155 separately prove the same-target circuit outcome in the running stack.
- **FR-003**: The extension MUST set `proxyDNS: true` (Firefox
  WebExtensions `proxy.ProxyInfo`) in the descriptor it returns from
  `proxy.onRequest` so that DNS resolution is delegated to the
  upstream SOCKS5 endpoint (SOCKS5h). **A privacy-critical test MUST
  verify that no DNS query for any `.onion` hostname leaves the host's
  network namespace during a routed Tor session** (US1 acceptance
  scenario 3 encodes this).
- **FR-004**: Non-Direct routing is fail-closed against a hardened
  target-browser profile. (a) The extension ships only in a release whose
  live-e2e hardening test (`tests/live-e2e/mullvad-browser-hardening/`) was
  green against a test profile that models the target browser's hardened
  defaults (DoH off, DoT off, HTTP/3 / QUIC off) — this is a **release-
  process** precondition, not a per-session runtime check. (b) At runtime,
  the extension gates WebRTC via the stable
  `browser.privacy.network.peerConnectionEnabled` API (the only hardening
  surface Firefox's stable WebExtensions API exposes — sol-review B4). If
  WebRTC is enabled at runtime, the extension MUST display a blocking
  dialog (architecture spec §14.5 failure UX) and MUST NOT route non-Direct
  requests through port 8881 until the user remediates. The extension does
  NOT claim to read or write the DoH/DoT/HTTP-3 preferences via the
  WebExtensions API; those three surfaces are release-cadence-verified, not
  runtime-enforced, and their post-verification drift is accepted residue
  (THREAT-MODEL §5.4/§5.5). (Aligns with Constitution Principle III bullet 3
  as amended by T091 — non-Direct routing is fail-closed at runtime against
  WebRTC; DoH/DoT/HTTP-3 are release-cadence-verified.)

#### Data plane behaviour

- **FR-005**: The data plane MUST listen on TCP `127.0.0.1:8881` for
  SOCKS5 (and HTTP CONNECT, per the architecture spec §4.1 protocol
  column) inbound connections from the browser. The port-to-upstream
  binding for port 8881 is fixed to the Tor sidecar at startup
  (Principle I — routing decisions are not made per request by the
  proxy).
- **FR-006**: The data plane MUST authenticate every inbound proxy
  request by extracting the bearer token from the SOCKS5 username/
  password pair (password = token) or, for any HTTP CONNECT framing it
  accepts on this port, from `Proxy-Authorization: Bearer <token>` in
  the CONNECT request. The candidate's verifier is computed once as
  `HMAC-SHA-256(pepper, candidate)` under the install-time pepper
  (data-model.md §1.5; T092 — Argon2id is retired, see SECURITY-DECISIONS.md)
  and compared with `crypto/subtle.ConstantTimeCompare` against every
  verifier in the current generation (no short-circuit on first match —
  the comparison loop's timing is independent of which slot matched)
  provided by the control plane (architecture spec
  §5.2 `ReloadTokens`). On absence or mismatch, the data plane MUST
  respond per the inbound protocol:
  - **HTTP CONNECT path**: HTTP 407 (Proxy Authentication Required)
    carrying the privacy-safe template body keyed
    `{CODE} = AUTH_REQUIRED`. Detailed contract:
    `contracts/error-template.md`.
  - **SOCKS5 path**: the 2-byte RFC 1929 sub-negotiation failure
    `0x01 0xFF`, then close the connection — no body, no template
    (the sub-negotiation framing has no body field). Detailed
    contract: `contracts/socks5-auth.md` §"Auth failure response".

  **The data plane MUST NOT include the offered token, its hash, or
  the rejected destination's hostname/port in any response, log, or
  counter increment.**
- **FR-007**: The data plane MUST forward authenticated inbound bytes
  on port 8881 to the Tor sidecar's SOCKS5 endpoint
  (`unix:///run/stargate-tor/tor-socks.sock` on the DP-only fabric), passing through the
  hostname-mode (SOCKS5h) target address and the SOCKS5 username
  unchanged. The data plane MUST NOT resolve the target hostname
  locally (Principle III). It MUST NOT parse, inspect, or modify
  request or response bytes beyond what SOCKS5 framing requires
  (Principle I).
- **FR-008**: The data plane MUST NOT log the destination hostname,
  the full URL, request or response headers, request or response
  bodies, or any per-request timestamp at finer resolution than the
  ≥1-hour aggregate bucket defined in architecture spec §6.4
  (`aggregate_counters`). Only the per-route, per-hour
  `(request_count, byte_count)` pair is recorded. Only requests that
  pass authentication increment `request_count`; auth failures leave
  the counter unchanged (Principle III — counting them would be a
  side channel for token-guessing attacks; `data-model.md` §3
  records the rule). Route failures (`ROUTE_DOWN`, `ROUTE_REFUSED`,
  `ROUTE_TIMEOUT`) DO increment `request_count` once authentication
  has passed: unlike auth failures they are not attacker-controlled
  in the same way (the attacker cannot induce a route failure at
  will without already routing), and the gap between `request_count`
  and the fraction of buckets with `byte_count > 0` gives the
  operator sidecar-health visibility at negligible privacy cost
  (data-model.md §3 records the asymmetry). **v1 persistence note**:
  in this feature, the aggregates live in data-plane process memory
  only; persistence to the `aggregate_counters` SQLite table via the
  CP→DP `GetStatus` pull (arch §5.2) is deferred to the admin-UI
  feature (data-model.md §3 / `contracts/control-grpc.md`
  §"GetStatus (minimum subset)", which authoritatively records both
  the in-scope test-harness caller and the deferred production
  caller). The invariant on *what* is counted (this FR)
  is independent of the deferral on *where* the counts persist.
- **FR-009**: When the Tor sidecar is unreachable (no TCP connection) or
  refuses the SOCKS5 target, the data plane MUST return a privacy-safe
  failure response with `{CODE}` chosen per architecture spec §10.1
  (`ROUTE_DOWN` / `ROUTE_REFUSED` / `ROUTE_TIMEOUT` as applicable) and
  shape chosen per the inbound protocol. The upstream dial/handshake
  result alone decides success or the route error; a `SidecarEvent`
  (`UNHEALTHY` / `STOPPED` / `CRASHED`) is an advisory hint and MUST NOT
  be a mandatory precondition for dialing or forwarding (Constitution
  Principle II; data-model.md §2; sol-review B3):
  - **HTTP CONNECT path**: HTML template from architecture spec §10.2
    with `{ROUTE_LABEL} = "Tor"` and the exactly-four headers
    enumerated in §10.3. Detailed contract: `contracts/error-template.md`.
  - **SOCKS5 path**: 10-byte RFC 1928 §6 reply with `BND.ADDR`/`BND.PORT`
    zeroed, then close. The `REP` mapping is `ROUTE_DOWN→0x03`,
    `ROUTE_REFUSED→0x04`, `ROUTE_TIMEOUT→0x06`; detailed contract:
    `contracts/socks5-auth.md` §"SOCKS5 request-phase failures (post-auth)".
  - **Both paths** MUST NOT carry destination, upstream, token, or
    sidecar-derived bytes in any field of the response.
- **FR-010**: Local DP route and CP admin/health listeners MUST bind loopback in
  their own namespaces and at host publication. LAN/VPS MUST use the actual tunnel
  interface in each listener namespace and remain closed on tunnel loss. No container
  environment flag, wildcard bind or tunnel elsewhere in the stack is an exception.
  T125's permission is superseded. T134 selected the topology; T162 implements it and
  T168 adds mandatory process confinement before admission, independent of auxiliary
  owner-rule persistence; T163 verifies production namespaces and packet outcomes. See
  `contracts/foundation-boundaries.md` §Deployment and authority.

- **FR-011**: The Tor sidecar MUST be configured with the directive set
  pinned byte-for-byte in `contracts/torrc.md §"Rendered file"`:
  `SocksPort unix:/run/tor-fabric/private/tor-socks.sock IsolateClientAddr IsolateSOCKSAuth`,
  `ControlSocket /var/lib/tor/control/tor-control.sock`, `CookieAuthentication 1`,
  `CookieAuthFileGroupReadable 1`, `DataDirectory /var/lib/tor`,
  `ClientUseIPv6 0`, `AvoidDiskWrites 1`, `UseBridges 0`,
  `Log notice stdout`, `SafeLogging 1`. For this static Tor-only slice
  the safe `torrc` is **baked into the Tor image at build time**
  (`sidecars/tor/Dockerfile`, T087) and loaded by the entrypoint at
  container start; the control plane does NOT render `torrc` at boot
  (Constitution Principle II — Compose starts Tor before the CP, so a
  CP-rendered `torrc` would couple Tor startup to control-plane
  availability; sol-review B2). `DataDirectory /var/lib/tor` is explicit
  because the entrypoint does not load Debian's `torrc-defaults`, so
  without the directive Tor would fall back to `$HOME/.tor` and land the
  control cookie at the wrong path (T087 / sol-review B2+M3).
  Control-plane-rendered `torrc` (atomic write into the
  `stargate-tor-config` volume) is future work for a dynamic-config
  feature and is deferred by T089 (T037 `TorrcRenderer` is deferred with
  it). Bridge lines MUST be absent from the image-baked `torrc` for this
  feature (bridges are a separate feature spec). **A contract test
  (`tests/contract/torrc/render_byte_match_test.go`, per T029) MUST
  verify the `torrc` template in `contracts/torrc.md` is byte-for-byte
  equal to the pinned Go golden** for v1 of this feature; T087's
  cold-volume regression test verifies the `/etc/tor/torrc` baked into
  the image equals the same golden without harness-seeded config.
- **FR-012**: Tor MUST have no TCP SOCKS or control listener or host port
  publication. Its native SOCKS Unix socket is in a Tor-private directory;
  the image-owned hook hardlinks that inode at mode 0660 into a DP-only
  volume. The DP may dial only that fixed path. The raw cookie-authenticated
  ControlSocket is in Tor's private state and is reachable only inside Tor
  for its native healthcheck and by the test harness via `docker compose exec`.
  CP holds no Tor cookie, Tor-cookie group, raw control mount or Docker network
  path. A separate CP-only fabric is reserved for T164's authenticated finite
  health observer. T164 implements and tests that endpoint and T165 validates
  its deployed caller matrix; until then CP health observation is unavailable
  and advisory, with no raw-control fallback (architecture spec §4.2).

#### Inter-plane integration

- **FR-013**: The data plane MUST accept a list of bearer-token verifiers
  (HMAC-SHA-256 tags under the install-time pepper; data-model.md §1.5,
  T092) via the gRPC `ReloadTokens` RPC (architecture spec §5.2) and
  apply it atomically. In this feature, the source of the list is a config
  file read by the control plane at startup (no dashboard UI yet; see
  Assumptions). The data plane MUST continue serving port 8881 with
  its last-known token list if the control plane is unreachable
  (Principle II; architecture spec §5.5). Stale proposals are rejected. Recovery MUST
  distinguish current authority from restored stale content; automatically renumbering an
  older backup to `current + 1` is prohibited by T156. T159 specifies the synchronized
  transition and durable acknowledgment contract before code. Admission is never gated on
  a control-plane event (data-model.md §2; sol-review B3): a request
  that authenticates against the last-known list reaches the upstream
  dial regardless of `SidecarEvent` state.
- **FR-014**: The control plane MUST emit a `SidecarEvent` with kind
  `STARTED` / `HEALTHY` / `UNHEALTHY` / `STOPPED` / `CRASHED` /
  `RESTARTED` for the Tor sidecar (architecture spec §5.2 events). The
  `detail` field MUST be a fixed-vocabulary token from the enum, not
  free text from Tor logs. The data plane consumes these events as
  **advisory local status/aggregate inputs** (data-model.md §2; Constitution
  Principle II): they MUST NOT be a mandatory precondition for listening,
  authenticating, dialing, or forwarding, and they MUST NOT
  short-circuit the upstream dial. The data plane MUST always attempt
  the fixed Tor fabric dial on every admitted request; the dial result
  alone selects `ROUTE_DOWN` / `ROUTE_REFUSED` / `ROUTE_TIMEOUT`.
  `SidecarEvent`s feed the audit journal (completed-hour operational categories under data-model.md §4) and status reporting only — a stale or
  forged event cannot suppress a dial that would succeed (Principle II:
  a compromise of the management UI cannot silently corrupt routing
  decisions). `RESTARTED` is informational.

#### Build and contract testing

- **FR-015**: The Tor sidecar image MUST be a Stargate-built image
  installing `tor` from the Tor Project's official Debian repository
  (`deb.torproject.org`) on a pinned Debian-slim base. Both the
  Debian-slim base **and** the final composed image MUST be pinned by
  sha256 digest in `compose/docker-compose.local.yml` (Principle IV).
  The Tor Project's signing key for the apt repository MUST be
  pinned by fingerprint in the Dockerfile and verified at build time.
  The Debian build inputs (base + every `apt-get install` package,
  including `tor`'s transitive closure) MUST be pinned to an immutable
  `snapshot.debian.org` run with explicit `=version` pins and retained
  sha256 hashes, so a clean rebuild selects byte-identical packages
  (T099; Principle IV). The trust rationale and rotation procedure MUST
  be recorded in `SECURITY-DECISIONS.md` and the architecture spec §7
  amended in lock-step to remove the `NEEDS CLARIFICATION` for the Tor row.
- **FR-016**: Contract-test suites under `tests/contract/**/` MUST exist
  and pass in CI before this feature merges. The v1 surface comprises
  six directories, each gating a distinct boundary the feature depends
  on: `tor/` (Tor sidecar behavioural invariants under the rendered
  config — port-exposure invariants (T019b); default-circuit fallback
  under `IsolateSOCKSAuth` when an upstream SOCKS5 client provides no
  username (T058a, pins the threat surface T047's outbound contract is
  defensive against); cookie-authenticated control-port helper (T062)
  consumed by tests under `torrc/` and `integration/`. SOCKS5h handshake
  on the rendered config is verified transitively by T029 (torrc/
  byte-match) and T033 (integration/ onion load); reachable-onion
  connection is verified by T033 directly; `GETINFO version` under
  cookie auth is verified transitively by any T062-consumer test
  passing — these three are intentionally not duplicated as `tor/`
  tasks per analyze finding E1: direct duplication adds CI bring-up
  cost without privacy gain); `torrc/` (rendered Tor config byte-match
  and
  per-invariant assertions); `socks5/` (port 8881 inbound SOCKS5
  demux, auth, leak invariants, counter side-channel resistance,
  request-phase failures); `error-template/` (privacy-safe error
  template invariants for all four codes plus leak-corpus scan);
  `control-grpc/` (inter-plane RPC + transport invariants for both
  UDS sockets). Adding a new
  `tests/contract/<surface>/` directory in a future feature
  automatically extends this gate.

#### Bearer token configuration (v1 manual flow)

- **FR-017**: The control plane MUST read bearer tokens from a config
  file at a documented path (`/etc/stargate/tokens.yaml` inside the
  control-plane container; mounted from a named volume the user
  populates manually for v1). The file format MUST be a list of token
  records, each with a label (free-form string, used in the audit
  log) and the **plaintext token** (the control plane computes the
  verifier `HMAC-SHA-256(pepper, token)` under the 32-byte install-time
  pepper at read time and never persists the plaintext beyond the file
  the user supplies; T092 — Argon2id is retired, see data-model.md §1.5
  and SECURITY-DECISIONS.md). Each plaintext token MUST be a 32-
  character lowercase-hexadecimal string (128 bits of entropy). The
  README quick-start documents `openssl rand -hex 16` as the canonical
  one-liner. Tokens that do not match the expected format MUST be
  rejected at config-load time with a static redacted error and an operational
  aggregate update; neither label nor offending token bytes may enter logs.
- **FR-018**: The control plane reads `tokens.yaml` **once at startup
  only** in v1. On a successful load, it MUST persist the verifiers and
  the bumped generation (from the `token_generation` record,
  data-model.md §1.8), push the verifier list to the data plane via
  `ReloadTokens` (FR-013), and aggregate operational categories under data-model.md §4.
  No labels, per-event timestamps or detail JSON may be journaled. Missing/unreadable/invalid
  input increments only the permitted category as specified and **does NOT call ReloadTokens** —
  the data plane keeps its last-known list and keeps serving port 8881
  (Principle II "continue routing"). Only a successfully-parsed explicit
  empty list (`tokens: []`) is the revoke-all path: that alone pushes an
  empty generation, after which the proxy returns `AUTH_REQUIRED` on all
  requests. A valid empty list and an I/O/parse failure therefore have
  distinct semantics, by design. Token add/revoke requires restarting
  the control-plane container; per architecture spec §11, the data plane
  keeps serving with its last-known token list across this restart.
  Filesystem-watch and SIGHUP-reload paths are explicitly deferred to
  the dashboard-UI feature.
- **FR-019**: The bearer token configured in the extension's
  `storage.local` MUST match one of the tokens in the control plane's
  config file. The extension UX for pasting/storing this token is in
  scope for this feature at a minimum level: an options page with a
  single field for the token, persisted to `storage.local`, with a
  visible warning that `storage.local` is not credential-grade storage
  (the canonical warning text is pinned in `data-model.md` §5.1; the
  rationale for accepting `storage.local` rather than a keyring path
  in v1 is in `research.md` §6 — Firefox ESR exposes no credential-
  grade storage API to extensions). The architecture spec §14.4
  `NEEDS CLARIFICATION` is **resolved-for-v1 by this FR** in
  combination with `research.md` §6; a future feature may revisit the
  decision if WebExtensions on Firefox ESR gain a credential-grade
  storage API.

### Key Entities

- **Bearer token (device token)** — a per-device opaque secret. Used as
  the SOCKS5 password and (where CONNECT framing is used) in the
  `Proxy-Authorization` header. Identifies *the device* to the data
  plane, not the user. Never persisted in plaintext outside the v1
  config file the user creates manually; stored as an HMAC-SHA-256
  verifier under the install-time pepper (T092) in the control-plane
  DB and the data plane's in-memory list.
- **Isolation partition / initiating site** — the authenticated-device, browser-profile and
  initiating-top-level-site tuple defined by the foundation boundary contract. Trustworthy
  browser navigation/document metadata selects the site; the destination is never a missing-context
  fallback. The extension sends only a fixed-length HMAC representation as the SOCKS5 username.
  Neither the clear site nor the isolation username is persisted by the data plane. Per-domain
  routing preferences remain a separate `storage.local` concern (out of scope here beyond
  architecture spec §14.4).
- **Tor circuit** — Tor's internal abstraction for an end-to-end path.
  Not directly observable by Stargate; queried only by the contract
  test against the sidecar's control port for verification. In normal
  operation no Stargate component sees circuit IDs.
- **Stargate aggregate counter** — `(route="TOR", hour_bucket,
  request_count, byte_count)` row in `aggregate_counters`
  (architecture spec §6.4). The only persistent record this feature
  creates about Tor traffic.
- **Privacy-safe error response** — the rendered byte sequence returned
  to the browser when a routed request fails. Defined by architecture
  spec §10; this feature instantiates it for the Tor-route error codes
  `ROUTE_DOWN`, `ROUTE_REFUSED`, `ROUTE_TIMEOUT`, and the
  feature-introduced `AUTH_REQUIRED`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time user with Mullvad Browser installed completes
  the steps "install Stargate extension → paste bearer token → load a
  known `.onion`" in **under 5 minutes** of wall-clock time on a
  reference workstation, **without** consulting any documentation
  beyond the project quick-start (`specs/001-tor-route/quickstart.md`
  in this feature; a top-level README will mirror or supersede it in a
  later feature). Measured by the walkthrough in T077 on a clean profile.
- **SC-002**: Over a run of **100 sequential CONNECTs, each labeled with
  one of 100 distinct first-party `.onion` domains** from the synthetic
  corpus published in `tests/integration/` — the corpus string is the
  SOCKS5 username, the isolation key the extension sends in production
  (FR-007) — the Tor sidecar reports **≥95 distinct circuit IDs** across
  the 100 streams (allowing some legitimate reuse), read through the
  control port (FR-012). This measures that stream isolation is in
  effect end-to-end through the extension and the data plane.
  *(Amended 2026-09-07, T061 escalation → amend-spec: the original
  wording — CONNECTs addressed TO the corpus strings — is unmeasurable
  on the pinned sidecar. Tor rejects the corpus addresses at parse
  (their embedded 32-byte keys are not valid Ed25519 public points, so
  the checksums valid per T063 A5 are beside the question), and for any
  unpublished-but-well-formed address it defers circuit construction
  until a descriptor arrives, which never does — no circuit exists to
  count. Probe evidence: T061 ticket §Notes; decision record:
  SECURITY-DECISIONS.md 2026-09-07. The isolation property, the corpus,
  the scale, and the threshold are UNCHANGED; only the addressing
  mechanism is corrected. The username is the isolation axis the shipped
  config actually enforces — `IsolateSOCKSAuth` keys circuits on the SOCKS
  auth identity, and the shipped torrc carries no destination-based
  isolation directive (SECURITY-DECISIONS.md 2026-09-07, T058 entry).)*
- **SC-003**: During a continuous **10-minute Mullvad Browser session
  loading only `.onion` content** through Stargate, a Wireshark capture
  on the host's loopback interface and on its egress NIC contains
  **zero** DNS queries (A, AAAA, MX, or otherwise) for any name ending
  in `.onion`. Canonical assertion: no DNS packet's query or answer
  fields contain a hostname matching `*.onion`. Wireshark/tshark
  display filter: `dns.qry.name contains ".onion" || dns.resp.name
  contains ".onion"`; expected zero matches across both interfaces.
  The per-PR gate (T034) implements the same assertion via `gopacket`'s
  DNS-layer parse; the release-tag measurement (T034a) and the
  operator quickstart sanity check use the display filter above.
- **SC-004**: For each of the four failure modes covered by the privacy-
  safe error template in this feature (`ROUTE_DOWN`, `ROUTE_REFUSED`,
  `ROUTE_TIMEOUT`, `AUTH_REQUIRED`), the rendered response contains
  **zero** values from the curated leak corpus
  (`tests/contract/error-template/leak-corpus.txt`), which includes:
  destination hostnames the test issued, the host's egress IP, Tor exit
  IPs from the consensus, sidecar version strings, sidecar log
  fragments, error backtraces, internal file paths. Measured by the
  contract test in §10.3.
- **SC-005**: The Tor-route data plane handles a sustained
  **≥200 concurrent `.onion` CONNECTs** in the integration test harness
  on the reference workstation, with no per-request allocation in the
  data plane forwarding hot path that retains beyond the request's
  lifetime (Principle I privacy and `stargate-perf` performance
  concerns both met). Measured by the `stargate-perf` agent's review
  pass against the data plane on completion of this feature.

## Assumptions

These are reasonable defaults the spec adopts where the input prompt or
the architecture did not pin a choice. Each is recorded so a later
clarification round (`/speckit-clarify`) can revisit them deliberately.

- **Local profile only for this feature.** LAN and VPS profiles
  (architecture spec §3 profiles) are explicitly out of scope here, per
  the user input. They are revisited in a separate feature spec once
  the local-profile slice is proven. FR-010 follows T156's actual-listener and
  host-publication loopback rule. T134 must replace the withdrawn T125 exception;
  its current topology is not evidence of compliance.
- **No bridges.** Tor bridge support (Constitution v1 Scope) is
  delivered as a separate feature spec. The `torrc` baked into the Tor
  image by this feature has `UseBridges 0` and no `Bridge` lines (FR-011).
- **Manual bearer-token configuration for v1.** The control-plane reads
  tokens from a yaml file the user populates (FR-017). The admin
  dashboard UI, including the enrollment flow with QR/JSON exchange
  (Constitution v1 Scope), is a separate feature; this feature only
  needs *some* bearer-token loading mechanism, and a config file is
  the smallest viable choice.
- **No Quarkus dashboard UI yet.** The control plane runs (it has to —
  it owns the token loader and the gRPC server to the data plane) but
  exposes no HTTP admin UI for this feature beyond a health endpoint
  used by `docker compose` healthchecks. The admin UI lands in a later
  feature; this slice deliberately defers it to keep the cone small.
- **Reference target onion service for the success-criterion tests.**
  The integration suite uses DuckDuckGo's v3 onion address
  (`duckduckgogg42xjoc72x3sjasowoarfbgcmvfimaftt6twagswzczad.onion`,
  long-lived and widely-cited; if it becomes unreachable the test
  harness must update the address and record the change in
  `SECURITY-DECISIONS.md`). For US2's circuit-isolation test, the
  harness uses a synthetic corpus of 100 distinct onion-style address
  *strings* presented to the SOCKS5 layer as the per-connection
  isolation key (the SOCKS5 username, FR-007); the sidecar's per-label
  circuit assignment is verified directly through the control port.
  *(Amended 2026-09-07, T061 escalation → amend-spec: the prior claim
  that "reachability is not required … only that the Tor sidecar
  attempts distinct circuits" toward the corpus strings is false on the
  pinned image — the sidecar neither parses them (invalid Ed25519 keys)
  nor builds any circuit toward an unpublished address; see SC-002's
  amendment note.)*
- **`AUTH_REQUIRED` is a new error code added by this feature.** The
  architecture spec §10.1 enumerates `ROUTE_DISABLED`, `ROUTE_DOWN`,
  `ROUTE_TIMEOUT`, `ROUTE_REFUSED`, `BIND_REFUSED`. `AUTH_REQUIRED`
  (HTTP 407 / SOCKS5 auth-fail equivalent) is added here for the
  bearer-token-missing/invalid case (Edge Cases & FR-006). The
  architecture spec is amended in lock-step with this feature's first
  implementation PR to record the new code; until that lands, the spec
  carries the addition as a known follow-up.
- **Reproducibility holds for the Go data plane in this feature.** The
  byte-reproducible build tier (Principle VI; architecture spec §12.1)
  applies; the `tests/reproducibility/` harness exercises the data-
  plane build twice and `cmp`s. Native-image reproducibility for the
  control plane is best-effort and is not load-bearing for this
  feature's success criteria.
- **Mullvad Browser / Firefox floor.** The extension uses WebExtensions MV2
  `proxy.onRequest`, native `publicSuffix.getDomain()` and document-bound request metadata as
  documented in architecture spec §14.1. The manifest sets Gecko `strict_min_version` to `153.0`,
  so older Mullvad Browser builds reject the extension rather than running a weaker isolation
  path. Alpha builds are development evidence only: v1 does not release until stable Mullvad
  Browser uses Gecko 153 or newer and retains MV2. If that stable release drops MV2, redesign and
  constitutional review replace this assumption; there is no silent legacy fallback.
- **`proxy.onRequest` failover timeout: Firefox default.** The router
  does not set `failoverTimeout` on the returned `proxy.ProxyInfo`
  descriptor; Firefox's 5-second default applies. Pinning the value
  would create a magic number with no spec-level rationale. If a
  future feature needs a tighter or looser failover (e.g. for
  high-latency bridge transports), the change ships with a
  justification in that feature's research doc and an amendment to
  this assumption. See tasks.md T054 for the v1 decision.
